### 3.1 三套编号的真相：一块 8 字节网格上的两种取法（本任务最重要的结构发现）

先把两张表的**真实字节**和**谁读它**钉死（静态，不需要 PS 运行）：

**(a) 静态表 `0x14b219bc0`**：21 条 `{dword 值, dword 4CC}` + 终止记录 `{35, 0}` @`0x14b219c68`，**PE `.data` 里就有初值**（文件偏移 `0xb217bc0`，本任务用 `pe_scan.va_to_offset` 直接 dump 核对）：

**(c) 两个翻译器读的是「从 `0x14b219bc0` 起、步长 8 的网格」**，不是「注册表数组」：

```asm
; 读：0x141b94090(rcx=&descHolder, rdx="textureBlendMode", r8=&obj+4)
0x141b940d2  call 0x142c4cbd0        ; 描述符里取整数值 -> ebx
0x141b940d9  call 0x141b94750        ; -> rax = 0x14b219bc0（两张表都在这块区域里）
0x141b940de  cmp  dword ptr [rax], 0x36      ; [0]==0x36 -> 终止
0x141b940e3  cmp  dword ptr [rax+4], ebx     ; 键匹配（+4 是键）
0x141b940e6  je   0x141b94103
0x141b940e8  add  rax, 8                     ; 步长固定 8
...
0x141b94103  mov  ecx, dword ptr [rax]       ; 值 = [0]
0x141b9410c  mov  dword ptr [rsi], ecx       ; *out = 值   <- 写进对象 +4
```

关键点：**运行期注册表从 `0x14b219c6c` 开始，而 `0x14b219c6c - 0x14b219bc0 = 0xac = 172`，不是 8 的整数倍**。于是网格把每条注册表记录「错位」半条来配对：

- `{值=35, 键=interned(hardMix)}`（记录起点 c68）—— 静态表的终止记录 `{35,0}` 的第 2 个 dword 恰好被构造器改写成了 `interned(hardMix)`，于是它成了一条**真记录**；
- `{值=30, 键=interned(linearDodge)}`（c70）、`{值=40, 键=interned(height)}`（cf0）…
- 4CC 键的条目同理：`{值=22, 键='Rvrt'}`（ca0）、`{值=10, 键='DdgS'}`（ca8）…

**所以「字面枚举」与「对象里的运行期模式号」对字符串键条目恒差 1**（字面枚举 −1 = 对象值），对 4CC 键条目是「前一记录的字面枚举」。这解释了上一轮 24 报告 §3.3 记的「第三套编号：multiply=7、linearHeight=41、height=40、subtract=39」——那不是第三套，就是这条网格规则。

**静态可复算**：一次性脚本 `sim_grid.py`（纯静态、不启动 PS）用「构造器立即数 + 网格遍历」预测 44 个模式的值；与本任务动态实测 **44/44 完全一致**（`mode-ids.json` 的 `agree_true: 44`、`agree_false: 0`）。

### 3.2 实验 A：Frida **spawn** 抓 `0x141b94750`（H4）的启动期执行

### 3.3 实验 B：57 步逐步切模式（JSX + attach 四面观测）

## 五、H2 / H4 复核结论（三选一）

### 5.1 H2 = `0x141a96230`：**证实**（纹理结构体 → 描述符写回）

- **静态**：函数内 5 条键名 `lea` + 对应取值（`0x141a962aa "textureScale"`←`[rdi+0x10]` double、`0x141a962d4 "invertTexture"`←`[rdi+0x20]`、`0x141a962f9 "protectTexture"`←`[rdi+0x21]`（仅当 `r9b` 非 0）、`0x141a96319 "textureBrightness"`←`[rdi+0x1c]`、`0x141a96338 "textureContrast"`←`[rdi+0x18]`）。
- **动态**：Frida 附着后 **169 次命中**，返回地址全部是 `0x141ef173b`（在 `0x141ef15c0` 内、H2 的静态调用者之一）。逐条读 `rcx` 结构体：

```text
(contrast,bright,scale,invert,protect) 序列（前 12 条）：
(-40,-8,52,1,0)  ← 附身前 PS 自己的工具状态（不是本实验设的）
(1,1,100,1,0) (1,1,100,1,0) (1,1,100,1,0)     ← 第 1 步
(2,2,100,1,0) ×3  … (57,57,100,1,0)           ← 第 57 步
```

  +0x18/+0x1c 的取值集合 = `{1,2,…,57}`，与我们**逐步写入的 brightness/contrast 标签**逐位相同；`+0x10`=`100.0` 与请求 `textureScale=100%` 相同；`+0x21`=0 与「未开 protectTexture」一致。
- **判据满足**：「参数以什么形态写回描述符」被运行期观测钉死 → **证实**。
- **一处异常如实登记**：`+0x20`（静态对应 `invertTexture`）**恒为 1**，而本实验从未设置 invertTexture。两种可能：(a) 这条写回路径的结构体 `+0x20` 语义不是 invertTexture；(b) PS 的纹理选项默认 `invertTexture=1`。本轮**未判定**，见遗留 L-3。

### 5.2 H4 = `0x141b94750`：**证实（启动期一次性初始化）** —— 并且**这次抓到了**

上一轮 24 报告写「附身时 PS 已启动完毕，必然错过，只能记未判定」。本轮用 **Frida spawn** 把时机抢在前面，结论从「未判定」升级为**直接观测**：

| 时点 | 观测 | 含义 |
|---|---|---|
| spawn 暂停态 `ms=6` | `regdump at-load-paused`：`nonzero_dwords=44`（全是静态表），`0x14b219c6c..d24` **全 0** | 运行期注册表**尚未构造** |
| resume 后 `ms=2007` | 仍 `nonzero_dwords=44` | 构造尚未发生 |
| `ms=10275` | **首次命中** `0x141b94750`，`ra=0x7ff7ba1c40de`（= `0x141b940de`，读翻译器的调用点） | 启动期第 10.3 s 第一次调用 |
| 同一次调用的 `onLeave`（`ms=10275`） | `nonzero_dwords=91`：23 条记录 + `"null"` 终止**全部就位**，且与构造器反汇编立即数**逐条相同** | 表由这一次调用建起来 |
| `ms=45013`（45 s） | 累计 **760 次**命中，表哈希**不变** | 之后每次调用都被初始化守卫挡回（早退） |

**结论**：H4 候选（「TransferMode 名字 → (标识, 字面枚举) 注册表构造」）**证实**；并且它是**启动期一次性初始化**（不是「排除」）。附带纠正一个措辞：**函数入口在运行期会被反复调用**（attach 运行 30 秒就命中 ≥700 次，见 §3.3 的 `H4-hit k=700`），所以「运行期下钩抓不到」只对「构造发生的瞬间」成立，对「函数入口」不成立——24 报告那句「本方法抓不到」应改为「本方法的附身时机错过了构造瞬间，但函数入口是可下的，只是要判断守卫早退」。

## 八、对下游（34/35/36 与 ABR 解析）的接口含义

1. **`src/brush_converter/mapping.py:31` 的 `_TEXTURING_MODE` 是「ABR 4CC/名 → Krita 值」的表**，它**不该**用本文的 `runtime_id` 当键（那是 PS 内部对象值）。真正能直接用的是 §4.5 的 11 行「PS 语义 → Krita 成员」。
2. **ABR 的 `BlnM` 是 4CC**，而 PS 的读翻译器匹配的键是「描述符里的整数值」：对 4CC 型模式就是 4CC 本身（`charIDToTypeID('Mltp')=0x4d6c7470` 命中静态表 `0x14b219be4`），对字符串型模式是 interned id（`height` 的 interned id **恰好就是 4CC `Hght`**，所以 ABR 里的 `Hght` 能直接命中；`linearHeight` 的 interned id 是 `0x916`，**不是** `LghH`）。
3. **修正 mode-align.json 的 7 个 4CC 名**（`SgdD→DdgS`、`MgdD→DdgM`、`HgdD→DdgH`、`SnrB→BrnS`、`MnrB→BrnM`、`HnrB→BrnH`、`ttsD→Dstt`）——本任务只写进 `mode-ids.json` 的 `name_corrections`，**没有改** `mode-align.json`（不属本任务写入范围，见遗留 L-1）。
4. **`Lght/Grdn/HdMxS`（Krita 的 LIGHTNESS=2 / GRADIENT=3 / HARD_MIX_SOFTER=11）在 PS 侧找不到入口**：转换器若把 ABR 里的某个模式映射成这三个 Krita 值，目前**没有 PS 侧依据**。这是 34/35/36 需要拍板的事。

### 2.2 为什么不用 Ghidra 引用图（承接任务 20/21 的硬事实）

- 任务 20 §7.2 实测：12 个键名字符串地址在 capstone 侧有 **49 条**引用指令，Ghidra `getReferencesTo` 只有 **1 条** → Ghidra 没为 `LEA` 取地址型引用建 Reference 对象。
- 任务 20 §7.1 第②行判定：**「偏移读写扫描」这类问题正解是遍历 `Listing.getInstructions()` 解析 disp8/disp32 + 基址寄存器**，与引用图无关。
- 因此本任务**不开 JVM**（也避免与 3 条并行线争 Ghidra 单实例锁），全部结论来自 capstone。

### 2.3 本任务的扫描口径（可复算）

1. 读 `.pdata` 得 438,177 个函数边界 `(begin,end)`；
2. 对每个函数**从函数起点线性反汇编**（capstone `CS_MODE_64`，`detail=True`）；
3. 只看内存操作数形如 `[base + disp]`、`base` 是**通用寄存器且不是 rsp/rbp/rip** 的指令（**剔除栈帧**：栈上局部变量偏移与结构体字段同形，不剔会得到瀑布级噪声）；
4. 记下 `disp ∈ {0x08,0x10,0x18,0x1c}` 且 **访问属性含 READ** 的指令地址，按 `(函数, 基址寄存器, disp)` 归并；
5. 取「同一 `(函数, 基址)` 上同时出现 0x18 与 0x1c」者为命中。

**扫描实测**：`funcs=438177 insns=30348749 hitfuncs=3450 349.6s`（脚本见 §8，输出 `cooccur.json`）

> 口径局限（必须一起读）：
> ① 函数边界来自 `.pdata`，`.text` 里有 6.66% 字节不在 `.pdata` 覆盖内（任务 20 §3.4），这些区间里的代码本任务扫不到；
> ② `lea` 指令被 capstone 标为「读内存基址」，所以 **`lea r8,[rdi+0x18]` 形式的「取地址传参」也会命中** —— 必须二次分类，见 §3；
> ③ 间接调用（`call [reg]`/vtable）静态不可解析，本任务只做直接 `E8` 调用边。

## 三、收敛方法（3450 → 10）

四道筛子，每道都写清判据：

| 级 | 判据 | 剩余 |
|---|---|---|
| 0 | 同基址同时读 +0x18 与 +0x1c | **3,450** |
| 1 | 去掉「只 `lea` 取地址」的传参函数，只留**取值读**（`mov/movzx/movsxd/movss/cmp/add/sub...`） | 3,135 消费型 / **93 纯传参** |
| 2 | 要求 +0x18/+0x1c **都按 4 字节**读（H1/H2 记载的 int32 形态） | **1,984** |
| 3 | 加「纹理子对象指纹」：同基址再出现 +0x20/+0x21（1 字节 bool）或 +0x08/+0x10 | 指纹分≥3 的只有 **9** 个 |
| 4 | 再用「锚点法」：谁调用纹理参数 IO 层（H1/H3/M4/L5）**且**同基址读 +0x18/+0x1c | **5 个**（0x141a8f520、0x141a90410、0x141a93cc0、0x141a8e060、0x141a964d0） |

| 锚点 | 说明 | 调用点数 | 调用者数 | 其中同基址读 0x18+0x1c |
|---|---|---|---|---|
| `0x141a939d5`（任务 11 记的 H1 入口） | 描述符→结构体（亮度/对比度/反相/保护） | **0** | **0** | — |
| `0x141a937e0`（H1 真入口） | 同上（含 4 条键名 `lea`） | **8** | **4**（0x141a8f520 / 0x141a90410 / 0x141ef1f90 / 0x141ef92e0） | 2 |

## 七、仍未判定的部分（如实登记）

1. **像素消费端未定位**。找不到任何函数能证明「读 `+0x18/+0x1c` 后拿 brightness/contrast 去算纹理像素」。
   - 已排除的解释：不是扫描没覆盖（438,177 函数全扫）；不是偏移记错（8 个跨模块拷贝函数交叉验证了布局）；不是「没人读」（3450 个函数读了）。
   - 剩下的解释（未证实）：① 语义在**运行期派生对象**上，字段类型从 int32 变成 float（#1 号候选 `0x141a8af30` 就是 float 形态）；② 消费端藏在**间接派发**后面（`call [rip+…]` / vtable）。直接证据：`0x1455a939f mov rax,[rcx+0xb8]` + `0x1455a93a2 call qword ptr [rip+0x2c1cd28]` —— 结构体方法经 `[obj+0xb8]` 取函数指针再间接调。
2. **两张模式表的数值关系未判定**：同一模式有两个数（Nrml：静态表 0 / 运行期表 0x16），**哪个数进 ABR 的 `BlnM` 未判定**。ABR 里 `BlnM` 存的是 4CC 字符串（`Mltp`/`Hght`/…），而运行期表的值是 0x0a..0x36 的整数，**两者之间的转换点未定位**。
3. **静态表与运行期表是否同一数组未判定**：运行期首条记录 `0x14b219c6c` 正好落在静态末记录 `0x14b219c68` 的后半（+4 字节），像是「覆盖/续写」，但没有证据判定设计意图。
4. **`Rvrt/SgdD/MgdD/HgdD/SnrB/MnrB/HnrB/ttsD/Str ` 9 个 4CC 的语义未判定**：按 4CC 缩写约定推断为 Revert / Dodge-{Shadow,Mid,Highlight} / Burn-{Shadow,Mid,Highlight} 变体，但**无 UI 字符串或行为证据**，只能等动态。
5. **`Lght/Grdn/HdMxS` 三个 `mapping.py` 成员在二进制里未定位** → 只能标「待动态确认」。若它们真存在，只可能在 `patt`/纹理资源的另一条路径上（本任务未扫）。
6. **间接调用断裂**：`call [reg]` / `call [rip+X]` 的静态不可解析（任务 20 §7.3-5 已认定为固有限制）。本任务只覆盖直接 `E8` 调用边，因此「调用者数」是**下界**。
7. **`.text` 里 6.66% 未被 `.pdata` 覆盖的字节**未扫（任务 20 §3.4）：那里可能还有未登记为函数的代码。
8. **本任务未做的事**：
   - 没下断点、没启动 PS（动态属 v0.3，任务 30/31）；
   - 没改 `src/`、`tests/`、`research/`，没写 `docs/数据/candidates.json`（那是任务 29 的产物）；

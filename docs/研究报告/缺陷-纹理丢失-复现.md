> 执行代理：bugrepro　|　日期：2026-11-20　|　工作目录：<REPO>
> 环境：Windows、Krita 5.3.3（git 858d352，安装于 <LOCAL_APP_DIR>\Krita (x64)）、
> 脚本解释器 <LOCAL_APP_DIR>\anaconda3\envs\brushConverter\python.exe（Pillow 12.3.0）
> 一次性脚本与产物：%TEMP%\brushconverter-team\bugrepro\（不入库）
> Krita 单实例：所有 GUI 实验用 %TEMP%\brushconverter-team\locks\krita.lock（mkdir 原子锁）串行。

## 一、结论（先说结果）

**在隔离 profile 中无法复现使用者报告的「纹理全部丢失 / 导入的笔刷彻底不可见」。**
把 v1.3.0 产物 bundle 放进隔离资源目录后，以下五层全部正常，且有多组数字互证：

| 层 | 判定 | 关键证据 |
|---|---|---|
| ① bundle 被 Krita 扫描/注册 | 正常 | 沙箱 cache 出现 storage_type_id=3（Bundle）、location 为 …18_test.bundle、active=1；paintoppresets 该 storage 下 19 条 |
| ② 19 个预设注册可见 | 正常 | 19 条 status=1（active），插件 resources("preset") 能按文件名取到；实测落笔 006/005/007/001/003 全部成功 |
| ③ 内嵌纹理被侧载（side-load） | 正常 | 未加载预设前 patterns 无 tex_；加载 006 后出现 tex_bb586e4480d4.png，加载 001 后出现 tex_79564f8784b9.png；v1.2.0 旧产物对应 tex_66e2987f.png / tex_69d92381.png |
| ④ 纹理参与渲染 | 正常 | 006 开纹理 vs 关纹理（同 .kpp 仅 Texture/Pattern/Enabled=false）：Alpha 均值 195.76 → 229.22；逐像素 mean 绝对差=26.47、最大 235、差异像素 56.65% 画布（bugaudit 独立复算）；texture mask mean=0.99951 std=0.0194，说明 006「看着像没纹理」是参数本身如此，不是丢纹理 |
| ⑤ 同名覆盖（旧产物→v1.3.0） | 正常 | 先放 v1.2.0 同名 bundle 扫描落笔（侧载 tex_66e2987f），再用 v1.3.0 同名覆盖并重启：预设仍 19 条 active，落笔侧载自动变为新名 tex_bb586e4480d4，Alpha 非零=8721，无旧 md5 残留、无 status 变 0 |

**唯一观察到的异常在使用者真实 profile 的 resourcecache.sqlite：**
PRAGMA integrity_check 报损坏（Page 30779: never used、resources_restypeid_index 与两个 sqlite_autoindex_resources_* 条目数不符）；
且在 10:41 的快照里，该 cache **完全没有** 我们 bundle 的任何记录（无 Bundle storage、无 19 个预设名、无 tex_ 资源）。
这与「换回 v1.2.1 也没恢复」相符——问题不在转换产物，而在使用者侧资源库状态。

**补充（本轮后补实验）：在「产物文件本身不完整/缺失」时，可以复现出与使用者描述等价的症状：**

- 实验 E3（bundle 文件被删、cache 里还有 storage）：Krita 下次启动把整包 storage 与 19 个预设一并静默删除 → 对应「导入的笔刷彻底不可见」；
- 实验 E5（bundle 被截断到 15 MB / 29.7 MB）：预设仍可见、可落笔，但内嵌纹理侧载失败且无报错（Alpha 8844 → 4672）→ 对应「纹理全部丢失」。

也就是说：**转换产物本身（完整文件）没有缺陷；使用者现场若出现这两种现象，最可能是他磁盘上的 .bundle 文件不完整（复制/覆盖中断、同步未完成、磁盘满）或资源目录状态异常。**

## 二、隔离手段（含两条失败路线，供后人避坑）

### 2.1 失败路线 A：APPDATA / LOCALAPPDATA 环境变量重定向（无效）

- 做法：env APPDATA=…\Roaming LOCALAPPDATA=…\Local krita.exe --nosplash。
- 观察：Krita 进程能起（脚本内 os.environ 的 APPDATA 确实是沙箱值），但**沙箱资源目录始终不生成 resourcecache.sqlite**；资源实际来自真实 %APPDATA%\krita。
- 原因：Windows 上 Qt/Krita 取 KnownFolder（QStandardPaths），不读 APPDATA/LOCALAPPDATA 环境变量。
- 结论：此路线作废。（lead 亦独立实测确认）

### 2.2 失败路线 B：--resource-location <sandbox>（资源隔离有效，但 PyKrita 插件不加载）

- 做法：krita.exe --nosplash --resource-location <sandbox>\res。
- 观察 1（资源隔离有效）：沙箱首次启动自动拷入 4 个默认 bundle、生成 KRITA_RESOURCE_VERSION 与 resourcecache.sqlite；放入 bundle 后 cache 里 storage/预设/纹理侧载均正常（见第三节 A/C/D 实验）。
- 观察 2（插件不加载）：**已知可用的 route-A 插件 tools/krita_render_gui_plugin.py 在此参数下也不加载** —— 插件装真实 %APPDATA%\krita\pykrita（同时也在沙箱 pykrita）、kritarc [python] 段 enable_bc_auto_render=true 已核对行号、Krita 主窗口正常出现（窗口标题 [Krita]），但插件模块从未 import（无 BC_AUTO_LOG、无结果 JSON），stderr 仅 4 行 pykrita 初始化信息。
- 原因（bugaudit 读源码 + 本实验互证）：--resource-location 只设 KoResourcePaths::s_overrideAppDataLocation；PyKrita 的桌面文件扫描 findAllAssets("data","pykrita/*desktop") 与模块查找 findAsset("pythonscripts", …) 走的路径不一致，插件被静默跳过。
- 结论：**要同时隔离资源 + 让 PyKrita 插件工作，不要用 --resource-location。**

### 2.3 最终采用：临时改 kritarc 的 ResourceDirectory（有效）

1. 备份真实 %LOCALAPPDATA%\kritarc（字节级），把其中 ResourceDirectory= 改成沙箱资源目录（正斜杠），并在 [python] 段插入 enable_bc_probe=true、sessionOnStartup=2；
2. 探针插件临时装到真实 %APPDATA%\krita\pykrita\bc_probe\（.desktop + __init__.py），沙箱 pykrita 也放一份；
3. 启动 krita.exe --nosplash（不带 --resource-location）；
4. 插件导出资源库快照 / 落笔 PNG / 结果 JSON 后自行退出；
5. finally 中按字节还原 kritarc、删除两处插件、杀掉新起 krita.exe。

隔离有效性核对（每次实验后）：
- 真实 %APPDATA%\krita\resourcecache.sqlite mtime 全程保持 10:55:03、大小 134,172,672 B 不变；
- 真实 %APPDATA%\krita\pykrita 只剩 preset_groups；
- kritarc sha256 还原为 1e562515c0b7ffc3b9392df6c2103ec92839d249357734a7f76bb77758831375（实验前值）。
- 注意：本机 kritarc 是 CRLF 行尾，早期补丁用 "[python]\n" 匹配失败导致 enable 键没写进去（表现为插件不加载）；已改为按行插入、兼容 CRLF。

## 三、实验与证据（命令 / 观察 / 数字）

通用说明：每次实验后读沙箱 resourcecache.sqlite（复制副本后只读查询）；Alpha 统计用 alpha_stats.py
（PIL：整图 Alpha 非零数、唯一值数、均值、标准差、按列均值的标准差）。

### 实验 A：干净沙箱 + v1.3.0 bundle（注册层）

命令（简化）：
python run_gui.py --label A-clean-v130 --reset --sandbox %TEMP%\krita-sandbox\gui --bundle <v1.3.0>\…18_test.bundle --timeout 180

观察：
- 沙箱 cache storages：id=5, type=3(Bundle), location=…\海怪笔刷-详情展示的勾线笔套装组18_test.bundle, active=1；paintoppresets 该 storage **19 条**。
- 启动扫描后 patterns 仅默认库（storage 1/2 各 81）+ memory 112，**没有 tex_**（尚未加载任何预设，符合 Krita 5.0 格式「按需侧载」的预期）。
- 总预设 295、图案 274（含默认库）。

### 实验 B：同一沙箱落笔（预设加载 + 纹理侧载 + 渲染）

命令：
python run_gui.py --label B-paint --sandbox %TEMP%\krita-sandbox\gui --timeout 150 --job "006_…kpp|…006.png|120|100|100" --job "003_…kpp|…" --job "001_…kpp|…"

插件日志（probe.log）：
before paint presets=163 patterns=37 → paint 006 alpha=8844 → paint 003 alpha=2738 → paint 001 alpha=12000
→ done jobs=4 presets=163 patterns=39 tex=['tex_79564f8784b9.png','tex_bb586e4480d4.png']

Alpha 统计（120×100 画布、100px 水平笔划、pressure=1.0）：

| 预设 | 非零像素 | 非零唯一值 | 非零均值 | 非零标准差 | 列均值 min–max |
|---|---|---|---|---|---|
| 006 大怪兽-碳铅（1920² 真实纹理） | 8844 | 255 | 195.76 | 79.71 | 88.58–227.79 |
| 003 大怪兽-圆头虚（无纹理） | 2738 | 111 | 245.88 | 30.91 | 5.0–250.58 |
| 001 勾线笔（1×1 占位纹理） | 12000 | 1 | 255.0 | 0.0 | 255–255 |

判读：006 的 Alpha 方差主要来自笔尖形状/压感；纹理本身对 Alpha 影响小（bugaudit 用 tools/texture_mask.py 算 006 mask mean=0.99951、std=0.0194；001/002 的 mask 恒 1.0）。
**因此「006/001 看起来没纹理」是参数本身的预期表现，不能当缺陷证据**；纹理参与的硬证据见实验 A2。

### 实验 A2：同一 .kpp 开/关纹理 + 清空 md5 变体

- 生成变体：make_variant_kpp.py 从 v1.3.0 bundle 抽 006，Texture/Pattern/Enabled 改 false（texoff）、
  清空 PatternMD5Sum 并删除 resource 标签的 md5sum 属性（nomd5），重建 PNG 的 iTXt preset 块。
- 观察：texoff 落笔 alpha=8813（同画布同笔划）；打开/关闭纹理两张图逐像素比较由 bugaudit 独立复算：
  **mean 绝对差=26.47、max 绝对差=235、差异像素(>2)=6798 = 56.65% 画布；Alpha 均值 229.22（关）→ 195.76（开）**。
- 结论：**内嵌纹理确实被侧载并参与渲染**。
- 附注：变体 kpp 与 bundle 内同名预设（资源名相同）会互相遮蔽——Krita.instance().resources("preset") 以资源名为 key，
  同名只保留一个。这也是本次 nomd5 变体没能落笔的原因（preset not found），但不影响上面的纹理结论。

### 实验 C：v1.2.0 旧产物（旧 8 位纹理名）对照

命令：python run_gui.py --label C-v120 --reset --sandbox %TEMP%\krita-sandbox\C --bundle <v1.2.0>…18_test.bundle --job 006/005/007

观察：cache storage 6 = Bundle（active），before paint presets=163 patterns=112；
落笔 006 alpha=8716、005 alpha=2008、007 alpha=10491；
done … tex=['tex_66e2987f.png','tex_69d92381.png']（**旧 8 位名**，来自 v1.2.0 内嵌 resource）。
Alpha（006）：非零=8716、均值 191.85、标准差 75.9。**旧产物同样有纹理、同样侧载成功。**

### 实验 D：同名覆盖（v1.2.0 → v1.3.0）再重启

命令：在同一沙箱 C 上覆盖 …\18_test.bundle（同名，内容换成 v1.3.0）后
python run_gui.py --label D-overwrite --sandbox …\C --bundle <v1.3.0>…18_test.bundle --job 006/005/007

观察：before paint presets=163 patterns=112；006 alpha=8721、005 alpha=2008、007 alpha=10415；
done … tex=['tex_1698a3618c68.png','tex_bb586e4480d4.png']（**自动变成 v1.3.0 新名**，说明 Krita 重新扫描了 bundle 内容）。
storage 仍为 Bundle 且 active；预设 status 无 0。**覆盖场景无异常。**

### 实验 E1：使用者真实 profile 的完整副本（含损坏 cache + storage 275）

做法：只读复制整个 %APPDATA%\krita（618 MB，含 resourcecache.sqlite、bundle、2×42 MB .abr）到
%TEMP%\krita-sandbox\E\res，ResourceDirectory 指向该副本。

观察：
- cache integrity_check 同样报损坏（Page 30779 + 索引条目数不符）；storage 275 = 我们的 bundle（active）；
  paintoppresets 各 storage 合计 360 条、patterns 143 条；ABR 两个 storage（22/271）只贡献 brushes，**没有同名预设冲突**。
- 落笔：006 alpha=8811（preset 名 大怪兽-碳铅【用数位板】）；勾线笔 alpha=3252；
  done … tex=['tex_2ab8ff79.png','tex_66e2987f.png','tex_bb586e4480d4.png']（我们的新名 + 两个旧 8 位名）。
- 结论：**连使用者真实 profile 副本里也复现不出「纹理丢失/笔刷不可见」**。

### 实验 E2：把 v1.2.1 产物放回使用者 profile 副本

命令：python run_gui.py --label E2-v121 --sandbox …\E --bundle <v1.2.1>…18_test.bundle --job 006

观察：before paint presets=360 patterns=143；006 落笔 alpha=8765；
done … tex=['tex_2ab8ff79.png','tex_66e2987f.png','tex_bb586e4480d4.png']。
**「换回 v1.2.1」在使用者副本里能正常工作**（v1.2.1 与 v1.3.0 的 22 个条目逐字节相同，见 lead 结论）。

### 实验 E3：bundle 文件缺失、cache 里仍有 storage（悬空存储）

做法：把 E 的副本再复制成 E3，**删掉 res 里的 …18_test.bundle 文件**，cache 不动，重启。

观察：
- 重启后 cache 里 **storage 275 被整条删除**，其 19 条预设也一并删除（SELECT COUNT(*) FROM resources WHERE storage_id=275 → 0）；
- Krita 侧 presets 从 360 降到 341；插件按文件名找 006 → preset not found；
- 另两支（勾线笔等文件夹存储）仍可用（alpha=3185）。
- **对应使用者描述的「导入的笔刷彻底不可见」：bundle 文件一旦不在资源目录，Krita 下次启动会静默把整包资源删掉（无报错、无提示）。**

### 实验 E4/E5：bundle 文件被截断/损坏（覆盖中断的典型后果）

做法：E4 先把 v1.3.0 bundle 截断为 15,000,000 B（原 29,697,202 B）重启；E5 为清理变体干扰后的同样实验。
（E4 首次运行时被 A2 遗留的同名变体 kpp 干扰，结论以 E5 为准。）

观察（E5）：
- cache 里 storage 5/17 仍 active=1，19 条预设 status=1（**资源库/数据库层面「正常显示」**）；
- Krita 侧 006 仍能找到并落笔，但 **侧载纹理列表为空（tex=[]）**，落笔 Alpha 非零=4672、均值 246.71、std 36.16
  （完整 bundle 同预设为 8844 / 195.76 / 79.71）；
- 全程无任何报错或对话框。
- **对应使用者描述的「纹理全部丢失」：bundle 文件不完整时，预设仍可见可画，但内嵌纹理侧载静默失败。**

**旁证：12 分钟窗口内 A2 的变体 kpp 与 bundle 同名预设发生遮蔽**，Krita.instance().resources("preset") 按资源名去重、
只保留一个 → 这也是「资源库能看到名字但对不上/选不中」的一个真实机制（E4 首跑即踩到）。

## 四、Krita 侧关键行为（源码要点，来自 Krita master 源码，bugaudit 提供 + 本组核对）

1. .kpp 解析入口 KisPaintOpPreset::loadFromDevice：QImageReader 读 PNG 文本块 version 与 preset；
   只有 version == "5.0" 才解析 resources 内嵌资源（我们的 .kpp 有 tEXt version=5.0，满足）。
2. 每个 resource 标签：先 resourcesInterface->source(type).exactMatch(md5sum, filename, name)，命中则复用现成资源，
   否则把 base64 字节包成 KoEmbeddedResource 侧载（side-load）。
3. 纹理图案解析 KisResourcesInterface::ResourceSourceAdapter::bestMatch：
   **md5 非空时必须按 md5 命中**，否则返回空（纹理静默禁用、无报错）；md5 为空才退回 filename/name 匹配。
4. KisPaintOpPreset::sanitizeSettings：Texture/Pattern/Enabled=false 时会删掉所有 Texture* 参数。
5. 内嵌图案侧载后是「临时资源」，**不落 resourcecache.sqlite**（本组实测：落笔后 cache 里没有 tex_ 行）；
   使用者真实库里的旧 8 位名 tex_ 行来自 Krita 原生 ABR 导入（Adobe Brush Library storage），与本项目产物无关。

## 五、失败点定位（本任务要回答的「哪一层」）

| 候选失败层 | 本组判定 | 依据 |
|---|---|---|
| bundle 根本没被加载 | 排除 | 干净沙箱与真实 profile 副本都生成 Bundle storage、active=1、19 预设 |
| 预设注册失败 | 排除 | 19 条 status=1；插件按文件名取到并成功落笔 |
| 内嵌纹理加载失败 | 排除 | tex_ 侧载名出现且开/关纹理 Alpha 差异 26.47（56.65% 像素） |
| 资源库状态被污染 | **可疑层之一，未能在副本中复现现象** | 使用者 cache integrity_check 损坏；10:41 快照中完全没有我们 bundle 的任何记录 |
| 产物文件缺失（用户侧文件问题，非转换代码） | **可复现等价症状** | E3：删掉 bundle 文件 → storage 与 19 预设被静默删除（笔刷不可见） |
| 产物文件不完整/截断（用户侧文件问题） | **可复现等价症状** | E5：截断到 15 MB → 预设可见可画、纹理侧载静默失败（Alpha 8844→4672，tex=[]） |

**未观察到的内容（如实记录）**：本组没有观察到「纹理全部丢失」「导入的笔刷彻底不可见」的任何一次；也没有观察到 cache 损坏本身导致 bundle 注册/侧载失败。

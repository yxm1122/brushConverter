## 0. 一句话结论

**我们的 .kpp 内嵌 patterns resource 写法与 Krita 5.x 自己的写法同构，md5 语义一致（都是 PNG/JPEG 文件字节的 md5）；
v1.2.1 追加的 tEXt 只改变「文件字节 md5」不改变像素，其作用是让内嵌资源躲开 Krita 的去重/撞车判定，属于保护而不是破坏；
本次「纹理丢失」在 .kpp 格式层没有找到可归因的偏差。** 真正可疑的方向在「bundle 是否被 Krita 注册 / 资源缓存 DB 状态」，
见 §8 候选机制（按可能性排序，含验证方法）与 §7 隔离实验。

## 3. md5 语义：三层全部按「文件字节」，不是像素数据

| 层 | 代码 / 实测 | 结论 |
|---|---|---|
| 我们的写出 | `preset_xml.py:_resource_xml`（`hashlib.md5(png)`，png=内嵌 PNG 字节）；`preset_xml.py:_apply_texture`（`PatternMD5Sum` 同一个 md5） | 文件字节 |
| Krita 内嵌资源校验 | `libs/resources/KoEmbeddedResource.cpp:31-34` `sanityCheckMd5()`：`KoMD5Generator::generateHash(m_data) == m_sig.md5sum`，`m_data` = base64 解码后的文件字节 | 文件字节 |
| Krita bundle 存储 | `libs/resources/KisBundleStorage.cpp::resourceMd5()` → `KoMD5Generator::generateHash(file bytes)`；`KoResourceBundle::resourceMd5()` 同样是 bundle 内文件字节的 md5 | 文件字节 |
| Krita 纹理查找 | `KisEmbeddedTextureData::tryFetchPattern`：`effectiveMd5Sum = PatternMD5Sum`（空则用 PatternMD5 反解）→ `bestMatchLoadResult(md5, fileName, name)`；`KisResourcesInterface::findResource`（`KisResourcesInterface.cpp:82-173`）先按 md5 查，md5 非空查不到时 bestMatch 才退到 filename/name | 用文件字节 md5 当索引 |
| 实测（原生样例） | brush：`9a90b42a…` == md5(PNG bytes) ✅，≠ md5(解码像素) ❌；pattern：`dc4e9099…` == md5(PNG bytes) ✅，≠ md5(像素) ❌ | 排除「像素 md5」假设 |
| 实测（我们的产物） | 22/22 资源 `md5sum` == md5(base64 解码字节)；9/9 纹理的 `PatternMD5Sum` == 对应资源 `md5sum` | 自洽 |

**由此可判定：**`PatternMD5Sum` 必须等于「内嵌字节（含 tEXt）的 md5」；写成像素 md5、源文件 md5 或省略都会让
md5 索引查不到（`bestMatch` 会退到 filename，但内嵌资源的 filename 只有资源真正被 side-load 后才有意义，见 §4），
这正是 `v3_badmd5` 变体要验证的情形。

### 3.5 内嵌资源在 Krita 5.x 里的完整生命周期（md5 在哪一步、哈希什么字节）

这一节是本审计最关键的源码链，逐行可核（行号对应 KDE/krita master 6fd9126）：

1. **加载 .kpp**：`KisResourceLocator::resource()`（`libs/resources/KisResourceLocator.cpp:331-354`）从 storage 取到预设后，第 352 行调用
   `loadRequiredResources(resource)`，源码注释写着「load all the embedded resources into temporary "memory" storage」。
2. **取 side-loaded 列表**：`KisResourceLocator::loadRequiredResources()`（同文件 :168-205）对每个
   `KoResourceLoadResult::EmbeddedResource` 执行 `importResourceDeduplicateFileName(sig.type, sig.filename, &buffer, "memory")`（:185）。
   注意：**只有 filename 参与导入**，signature 里的 md5 在这一步不用于校验；重名时文件名会被改成带 `_embedded_` 的版本。
3. **导入 memory storage**：`KisResourceLocator::importResource()`（:560-642）先 `storage->importResource(url, &buf)`，再从 storage 读回资源，
   第 612 行 `resource->setMD5Sum(storage->resourceMd5(url))`，第 620 行 `KisResourceCacheDb::addResource(...)` 写库。
4. **memory storage 存的是原始字节**：`KisMemoryStorage::importResource()`（`libs/resources/KisMemoryStorage.cpp:203-224`）
   执行 `storedResource.data.reset(new QByteArray(device->readAll()))`——原样保存传入的字节，不重新编码。
   `KisMemoryStorage::resourceMd5()`（:321-339）对该字节数组做 `KoMD5Generator::generateHash(*storedResource.data)`。
5. **md5 算法**：`KoMD5Generator::generateHash(const QByteArray&)`（`libs/resources/KoMD5Generator.cpp:12-23`）=
   `QCryptographicHash::Md5` 直接对字节数组求哈希。
6. **storage 型资源（bundle / folder）**：`KisResourceCacheDb::addResources()`（`libs/resources/KisResourceCacheDb.cpp:1238`）
   `resource->setMD5Sum(storage->resourceMd5(verIt->url()))`；`KisBundleStorage::resourceMd5()` → `KoResourceBundle::resourceMd5()`
   读 zip 内该文件的字节求 md5。

**因此：内嵌 patterns 在 Krita 里最终注册进 DB 的 md5 = md5(内嵌的原始字节) = 我们 XML 的 `md5sum` 属性 = `PatternMD5Sum`；**
它与解码后的像素无关，也与 Krita 是否重新编码 PNG 无关（memory storage 原样存字节，不重编码）。

补充一条容易误判的事实：`KoEmbeddedResource::sanityCheckMd5()`（`libs/resources/KoEmbeddedResource.cpp:31-34`）比较的确实是
「XML `md5sum`」与「base64 解码后字节的 md5」，但它在**生产代码里没有被调用**——全仓库只有测试
`libs/image/tests/KisPaintOpPresetTest.cpp:79` 调用它。所以 XML 的 `md5sum` 写错不会让 Krita 判「资源无效」，
只会影响 `loadFromDevice` 的 `exactMatch` 去重（签名里的 md5 参与去重，见下）。

**去重与取用的判定规则（决定「纹理会不会静默失效」）：**

- 去重（加载 .kpp 时）：`KisPaintOpPreset::loadFromDevice` 调 `exactMatch(md5, filename, name)`
  = `findResource(..., exactMatch=true)`（`libs/resources/KisResourcesInterface.cpp:82-112`）：**只要按 md5 找到任一同 md5 资源，就跳过内嵌资源**
  （filename/name 只影响 penalty：inactive +100、filename 不符 +2、name 不符 +1，不会让它变成「没找到」）。
  被跳过的内嵌资源**不会**被导入 memory storage。
- 取用（纹理实际查找）：`KisEmbeddedTextureData::tryFetchPattern` 用 `bestMatch`：先按 md5（`resourcesForMD5` 查 `versioned_resources.md5sum`，
  **无 active/status 过滤**，`KisResourceModel.cpp:360-390`）；找不到再按 filename；再按 name。三步都空 → `FailedLink`。
- 兜底：`tryLoadEmbeddedPattern` 只有在旧格式内嵌了 `Texture/Pattern/Pattern`（inline base64）时才可用；**我们的产物不写这个字段**，
  所以 `FailedLink` = 纹理静默禁用（无报错、无 UI 提示，Alpha 退化为无纹理）。

**推论：**纹理能否显示，只取决于「(a) 内嵌资源被 side-load 进 memory storage」或「(b) 资源库里有一份按 md5/filename/name 能加载到的同源图案」。
两者都不成立时就是用户看到的「纹理丢失」。

## 4. tEXt 判定：是保护，不是破坏

### 4.1 机制（Krita 源码）

`KisPaintOpPreset::loadFromDevice`（`libs/image/brushengine/kis_paintop_preset.cpp:168-256`）：

1. `version = reader.text("version")`，只接受 `2.2` / `5.0`；
2. 仅当 `version == "5.0"` 且存在 `<resources>` 时逐条读 `<resource …>`：
   - `existingResource = resourcesInterface->source(type).exactMatch(md5sum, filename, name)`
   - 命中则 `continue`（跳过该内嵌资源，改用资源库里已有的那份）
   - 未命中才 `QByteArray::fromBase64(e.text())` → `KoEmbeddedResource` → `sideLoadedResources`
3. 纹理参数在 paintop 创建时才解析：`KisEmbeddedTextureData::tryFetchPattern` 用 md5 在（全局 + side-loaded）资源源里 `bestMatch`。

所以 tEXt 的唯一作用：让内嵌 PNG 的**文件字节 md5** 与「用户图案库里可能存在的同像素图案」不同 → 第 2 步 `exactMatch`
不会命中 → 内嵌资源总会被 side-load。它不改变像素、不改变 PNG 结构合法性、也不参与任何「资源无效」判定
（无效判定只有 `sanityCheckMd5`，而我们已经自洽）。

### 4.2 实测：tEXt 版 vs 无 tEXt 版像素完全相同

`variants/v1_ours_tex.kpp`（tEXt，11442 B，md5 `9ffc884b…`）与 `variants/v2_notext.kpp`
（无 tEXt，11344 B，md5 `75f0bc21…`）：Pillow 解码后 **pixels identical: True**（shape (64,64,3)），
只有字节 md5 不同。这与 Krita 用 QImage 解码内嵌图案的路径一致——tEXt 只是元数据块。

### 4.3 反向证据（团队既有 A/B，引用不重跑）

`docs/验收报告/实验-Krita侧-报告.md` §8 已做过字节级 A/B（本任务复验其结论，不重复其 52 张全量）：

| 变体 | Alpha 表现 | 结论 |
|---|---|---|
| 源字节逐字节内嵌（与库内图案同 md5） | Alpha 恒 255 | 纹理被静默禁用（md5 撞车坑） |
| 同像素、只改 pHYs（md5 变） | 正常，与掩码预测逐像素一致 | md5 唯一即可 |
| **tEXt 标记（v1.2.1 做法）** | 正常 | 规避成立 |

本次隔离实验（§7）在 Krita 5.3.3 上重做最小 A/B（tEXt / 无 tEXt / md5 错配 / 库内同 md5 撞车 / 原生样例）。

**结论：tEXt 不是本次「纹理丢失」的原因；它在本轮之前就是规避 Krita md5 去重坑的手段，本身不引入任何格式不合法。**

| 全库 patterns | 300 条、inactive=0、无与我们纹理同 md5 的图案 |
| **memory storage 的 patterns 行** | **NONE** —— 说明真实 profile 里从未真正加载过任何带内嵌纹理的预设（一旦加载，内嵌 pattern 会以 storage=memory 写进 DB） |

**结论：**本简报上游「用户 profile 没有 Bundle storage」是**一个时点状态**，不是稳定事实——当前 DB 里该 bundle 已注册且 19 个预设全部 active。
（注册时间无法从 DB 直接读出：`storages.timestamp` 与 `versioned_resources.timestamp` 记的是 bundle **文件 mtime**，本例为 10:10:16；
但 `memory` storage 的时间戳 10:55:01 说明 10:55 确有一次真实 profile 的 Krita 启动，很可能就是它完成了注册。）
另外要警惕队友工具 `tools/krita_render_runner.py` 每次运行会**备份并还原** `resourcecache.sqlite`——如果某次渲染用的备份早于 bundle 导入，
还原动作会把已注册的 storage 行「抹掉」，从而制造出「明明文件在、storage 却没了」的假象。**复核注册状态必须用最新 DB 快照。**

## 8. 回答 lead 的四个问题（要点）

### ① 内嵌 patterns resource 在 Krita 5.3.3 里何时被注册/加载？是否要求 resource 名与 md5 索引一致？

- **bundle 扫描阶段不解析 `<resources>`**：只把 .kpp 当「一个资源条目」登记进 DB（`KisResourceCacheDb::addResources` 为预设计算缩略图/md5，但不展开内嵌资源）。
- **内嵌资源在 .kpp 被「按需加载」时解析并注册**：资源库/笔刷箱真正取用该预设时，`KisResourceLocator::resource()`
  （`KisResourceLocator.cpp:331-354`）→ `loadRequiredResources()`（:168-205）→ 每个内嵌资源按 filename **导入 memory storage**
  → `importResource()`（:560-642）写 resources/versioned_resources 表（storage=memory），md5 = `KisMemoryStorage::resourceMd5`
  = md5(原样保存的内嵌字节)。完整链与行号见 §3.5。
- **不要求「预先存在 md5 索引」**：注册时 md5 由字节现算；但要求 `PatternMD5Sum` == md5(内嵌字节)，否则 md5 查找失败、只能靠 filename/name 兜底。
- **去重发生在更早一步**：`KisPaintOpPreset::loadFromDevice` 的 `exactMatch(md5,filename,name)` **只看 md5** 决定是否跳过内嵌资源
  （命中即跳过，不会再导入 memory storage），见 §3.5「去重与取用的判定规则」。

### ② tEXt 会不会让「同名资源 md5 冲突检测」仍判撞车、或反过来判资源无效？

- 不会「仍判撞车」：撞车（去重跳过）的判据是 `exactMatch(md5,...)` 在全局资源库里按 **md5** 命中；tEXt 把 md5 改掉后不命中 → 内嵌资源被 side-load 并导入 memory storage。
- 不会「判资源无效」：`KoEmbeddedResource::sanityCheckMd5()` 在生产代码里**根本没有被调用**（只有测试 `KisPaintOpPresetTest.cpp:79`），
  所以即使 XML md5 写错也不会「判无效」；真正影响的是去重命中率与 `PatternMD5Sum` 的查找命中率。
- 也就是说 tEXt 让「同像素不同字节」成为常态，正好绕开 Krita 的 md5 去重；风险只在「`PatternMD5Sum` 与字节 md5 不一致」的写法，而不是 tEXt 本身。

### ③ 1920×1920 大图案与 1×1 占位在加载路径上有差异吗？

- 加载路径完全相同（base64 → QImage 解码 → pattern 资源）；Krita 没有尺寸上限检查（`KoPattern` 只要求 width/height>0；`loadPatFromDevice` 是 .pat 分支，与本例无关）。
- 现实参照：`JP_Essential_Brushes_1.2.1.bundle` 里内嵌 patterns 最大 **10,228,132 B（3264×2448 JPEG）**，说明 Krita 5.x 完全接受 MB 级内嵌图案。
- 差异只在成本：7 个大纹理预设每个 .kpp 3.3–4.4 MB、bundle 29.7 MB；每个预设加载时约 4 MB base64 解码 + PNG 解码（一次性），无超时机制。
- **1×1 不是占位符**：ABR 里 `R. Melentyev's Art Texture` 图案本身就是 1×1 RGB（patterns 区实测），PS 侧同样没有可见纹理感；它被误判为「纹理丢失」是可能的。

### ④ 「真实 profile 里看不到纹理/笔刷」候选机制清单（按可能性排序 + 验证方法）

| # | 机制 | 为什么符合现场 | 验证方法 |
|---|---|---|---|
| 1 | **bundle 的注册是「启动时一次性」的，覆盖后没有完整重启**：`findStorages/synchronizeDb` 只在启动跑；用户覆盖 .bundle 后若只切窗口/没真正退出重启，新内容不会被扫描登记 → 预设/纹理都还是旧的或不可见 | §6.1 实测：重启一次后 bundle 就被登记（19/19 active）；而 lead 早前快照里没有这行，属「覆盖后未重启」的时段 | 对照文件 mtime 与 Krita 启动时间；重启 Krita 一次再看 `storages`；用 `diagnose_profile.py` 对比前后快照 |
| 1b | **团队工具把注册行还原掉**：`tools/krita_render_runner.py` 每次渲染前备份、结束后**还原** `resourcecache.sqlite`；若备份早于 bundle 导入/重启，还原会把已注册 storage 行抹掉，制造「文件在、storage 没了」的假象（也会让资源库里的预设消失） | 本轮排查中真实 profile 的 DB 被多次改动（`memory` storage 时间戳 10:55:01、lead 快照有 id=271 现在没有） | 任何结论前用最新 DB 快照 + `diagnose_profile.py` 复核；避免在真实 profile 上跑会还原 DB 的工具 |
| 2 | **覆盖 bundle 后旧 storage 记录陈旧/失活**：DB 里 `location` 相同但 `active=0` 或资源行属于旧 bundle | 「覆盖旧产物」正好是这个动作；换回 v1.2.1 也没恢复 → 指向 DB 状态而非文件 | 查 `storages.active` 与 `resources` 行；在副本里删掉该行重启看是否重建 |
| 3 | **同 md5 图案去重命中且库内那份不可加载** → 内嵌被跳过（不会导入 memory storage）+ `bestMatch` 的 md5→filename→name 三步全空 → `FailedLink` → 纹理静默禁用（我们没写 inline `Texture/Pattern/Pattern` 兜底） | 历史 A/B 见过（§4.3）；今天通过源码链确认了完整机理（§3.5）。tEXt 能规避「同字节」，规避不了「同一份 tEXt 字节曾被另一个已删/失活 bundle 注册」 | 副本里预置同 md5 图案（active/inactive 两种）再渲染；对应用例 v5/v6 |
| 3b | **memory storage 里的陈旧记录被复用**：内嵌图案会以 storage=memory 写进 DB；若同名（`resources.name`）旧行还是 status=0（inactive），`KisResourceModel::addResource`（`KisResourceModel.cpp:915-983`）会走「更新旧行」分支并把 `resource->setMD5Sum(旧行 md5sum)`（:977）——旧 md5 与当前字节不同时，后续 md5 查找失败，只能靠 filename/name 兜底 | 用户反复覆盖产物 → 旧 memory 行残留；DB 里确实有 storage=memory 的历史行（用户库现有 2 条 gradients） | 隔离副本里先伪造一条同名 status=0 的 memory pattern 行再加载我们的预设，观察纹理是否失效 |
| 3c | **启动同步阶段 DB 事务失败**：`KisResourceCacheDb::addResources` 用 `QSqlDatabase::database().transaction()` 逐条插资源；若 DB 被另一实例占用/有残留 WAL/磁盘满，插入失败 → `addStorage` 返回 false → 该 bundle 静默不注册（仅 stderr 有 `Could not execute addResource statement`）；已有 DB 资源仍能显示，正好像「资源库正常但新笔刷不可见」 | 用户是「覆盖产物」后出问题，覆盖时若 Krita 未完全退出，DB 可能处于异常状态 | 隔离副本里人为锁 DB 或塞只读文件后启动，看 storages 是否缺行 + stderr 关键字；用户侧看启动时是否弹过「资源数据库同步失败」 |
| 3d | **覆盖后文件名变了**：v1.2.1 产物名与 v1.3.0 不同（用户现场文件叫 `…_test.bundle`），旧 storage 行指向已不存在的旧文件名；新文件名那次启动未完成扫描/同步 | 现场 DB 里既没有新文件名行，也可能残留旧文件名行 | 查 `storages.location` 是否存在指向已删除文件的 bundle 行；对比用户覆盖前后的文件名 |
| 4 | **用户操作层**：资源库按 tag/搜索过滤，或资源管理器里 bundle 未启用 | 「资源库正常显示，但导入的笔刷彻底不可见」符合过滤/未启用表现 | 使用者清空搜索、看 All 标签、看资源管理器启用勾选 |
| 5 | **1×1 纹理无可见纹理感**（001/002 两支勾线笔） | 这两支纹理由 ABR 决定，PS 里也不可见 | 对比 PS 里同两支的纹理开关效果 |
| 6 | 其它存储/权限问题（文件权限、杀软锁定、路径特殊字符） | 概率低但存在 | `dir /r` 看 ADS、换目录启动、看 Krita 日志 |

**关键推论：**机制 1/2 属于「bundle 登记/缓存」问题，机制 3 属于「md5 去重」问题；两者都与 .kpp 内嵌 resource 的格式写法无关，
所以本报告不建议为「纹理丢失」改 .kpp 格式。

## 9. 最小修复方案（格式层）

**结论：格式层不需要修。** 现有写法（content-hash 命名 + tEXt + `PatternMD5Sum`=字节 md5 + `PatternMD5` 留空）
在 Krita 5.x 语义下是最干净的可自包含写法：

- 命名保证「同名 ⇒ 同内容」，避免同名串用；
- tEXt 保证「同像素 ⇒ 不同 md5」，避免 md5 去重；
- `PatternMD5` 留空避免 Krita 自己写二进制导致的 XML 非法字符坑（Krita 自己都要在加载时删掉它，见 `kis_paintop_preset.cpp:189-193`）。

若后续因其它原因必须动，最小变更只有一处（**本次不实施，不改 src/**）：
保持 `src/brush_converter/kpp/preset_xml.py` 的 `_apply_texture()` 中
`set_string("Texture/Pattern/PatternMD5", "")` 不变。反而建议在 `docs/developer-guide.md` 坑清单里补：
「`PatternMD5` 必须留空；Krita 自己的写法是 16 字节二进制，会在 XML 里产生非法字符，加载时被 Krita 自己删除」，
以及排查提示「bundle 文件存在 ≠ 已注册；判断依据是 `resourcecache.sqlite` 的 `storages` 行」。

## 0. 结论摘要（先给结论）

1. **未找到「可直接采用」的 PS→Krita 亮度/对比度映射公式。** 7 个候选映射在 148 张 PS 真值图上
   全部落在「不合格」（最差差异比例 100.00%，平均 77.94%–90.89%），其中包含**现有经验公式基线**
   （平均 80.83%）。→ 下一任务指向 **任务 11（逆向 PS 本体）**，不是任务 13。
2. **跨引擎基线差异本身已经超过判据上限**：同一纹理、同样 0/0 参数下，Krita 算法复刻与 PS 真值的
   差异比例是 **22.36%–100.00%**（12 组可核验）。只要判据是「PS 图 vs Krita 图逐像素差异 ≤2%」，
   任何参数映射都不可能合格——这不是公式写得对错的问题，是基线不平。
3. **真正被核验到的成果在 PS 一侧（A 轴）**：在纹理深度 **d100** 且模式属于「位移型」的四组上，
   PS 的亮度处理**逐像素精确等于一维平移**（差异比例 **0.00%**，最大差值 0，MAE 0.00）：
   减去用 clip(base − B)，变暗/正片叠底/线性加深用 clip(base + B)；对比度是**以 127.5 为中心的分段倍率**
   （f=1+C/100 (C<0)、f=1/(1−C/100) (C>0)，差异比例 **0.57%**，合格）。
   这一条在 `research/测试结果2` 与并行任务的独立纹理（`ps__自动纹理A__*`）上**各复现一次**。
   但它描述的是 **PS 内部行为**，不是 Krita 参数映射，不能直接交给任务 13。
4. **深度 <100 与 Height/Linear Height 系列的亮度/对比度无法用「最终图上的 LUT」解释**：
   d60/d10/d6/d5/d2 组全部不合格（最优候选也没有一组能让全组 ≤2%）。说明这些情况下亮度/对比度
   作用在**纹理层/合成之前**，或参与模式内部的非线性合成——这正是任务 11 要查清的位置。
5. **PS 参数交叉核对已实际执行成功**（PS 26.9.0）：PS 自己把 textureBrightness=−27 / textureContrast=−17 /
   textureDepth=41 / textureScale=53 原样读回，与我们 ABR 解析器解析出的软铅实测值完全一致；
   9 支纹理笔刷的解析值范围（b −31..40、c −50..6、depth 4..55、scale 20..73）全部落在 PS 接受范围内。

### 1.2 工具与口径（写死）

- 差异比例：`tools/imgdiff.diff_alpha()`，tol=2 灰度级，分母为 W×H 全部像素（不是非零像素数）。
- Krita 侧渲染：`tools/texture_mask.compute_mask()`（任务 07 按 Krita 源码逐行复刻，对 `research/krita结果/`
  23 张真值图实测差异比例 0.00%、最大差值 ≤1 灰度级）。
- 判定：**≤2% 合格 / 2%–10% 部分合格 / >10% 不合格 / 无法核验（写明原因）**；
  一个候选只要有一张适用图不合格就不判合格（以最差图为准，不用平均值掩盖失败）。
- 预测图写到系统临时目录仅供 imgdiff 读取，**不写入仓库、不修改任何真值图**。

### 1.3 三轴设计（为什么必须分轴）

| 轴 | 输入 → 输出 | 真值 | 回答的问题 |
|---|---|---|---|
| **A 轴** PS 侧行为 | PS 同组基线图 b0_c0 → 套候选的亮度/对比度变换 | PS 同参数图 | 候选是否描述了 **PS 自己**的行为 |
| **B 轴** PS→Krita 映射 | 候选把 PS(b,c) 换算成 Krita(Brightness,Contrast) → Krita 算法复刻渲染 | PS 同参数图 | 候选能不能**直接拿去用**（设了 Krita 参数后画面是否和 PS 一致） |
| **C 轴** 跨引擎基线 | Krita 算法复刻 B=0,C=1 | PS 基线图 b0_c0 | 「绝对逐像素 ≤2%」这个判据本身是否可达 |

分轴是必须的：PS 与 Krita 是两套引擎，同一纹理同一参数也会画出不同结果（见 §4.3），
把跨引擎差异（C 轴）算到公式头上（B 轴）就会得出错误结论。

### 1.4 分组过滤规则（防止「伪失败」）

亮度候选只在「对比度=0、亮度≠0」的图上核验；对比度候选只在「亮度=0、对比度≠0」的图上核验；
组合候选用全部非基线图。理由：若拿亮度候选去比对比度图，差异必然 100%，那是测量错误不是公式错误。

| A8 | 本次调研组合推导 | 先 base+B，再 (·−127.5)*f+127.5，clip | 全部 | 同上，亮度取正 |

**A 轴结论（可执行、有数字）**：

- **d100 + 位移型模式**：亮度是**精确的一维平移**，方向随模式改变——
  减去: out = clip(base − B)；变暗/正片叠底/线性加深: out = clip(base + B)；差异比例 0.00%、最大差值 0、MAE 0.00。
- 对比度：f=1+C/100 (C<0)、f=1/(1−C/100) (C>0)，以 **127.5** 为中心；
  在 减去/变暗/正片叠底/线性加深 的 d100 组上差异比例 **0.57%**（≤2%，合格；剩余差异来自四舍五入），
  改成 pivot=128 就升到 25.89%（不合格）——说明中心点必须取 127.5。
- 亮度方向**不是全局统一**：减去是 −B，其余是 +B；A1 在 减去 上 100%，A2 在 变暗 上 100%，
  这就是「用一条统一公式覆盖所有模式」必然失败的原因。
- **深度 <100 或 Height/Linear Height 系列：任何「最终图上的 LUT」都不成立**（最优也 26%–100%）。
  说明亮度/对比度在这些情况下作用在**纹理层/合成之前**，或与模式内的非线性项耦合——这是任务 11 要定的位置。

### 4.4 PS 参数交叉核对（JSX 实跑，PS 26.9.0 / Photoshop 2025）

**执行方式**：Photoshop.exe -r "tools/ps_read_params.jsx"（无需 pywin32/COM），
原始输出见 docs/研究报告/ps_read_params.log，末尾 READ_PARAMS_DONE。
脚本用 Action Manager 的 currentToolOptions 读写画笔纹理参数（类名 paintbrushTool）。

**(a) PS 自己读回的参数名/值（中性写入后）**：
useTexture=true, textureScale=100, textureBrightness=0, textureContrast=0, textureDepth=100, textureBlendMode=height，纹理图案名 ps_read_params_tex。

**(b) 用我们 ABR 解析器的真实值写入再读回（对照表）**：

| 项 | 我们解析器解析出的值（tests/海怪笔刷-...18支.abr） | JSX 写入值 | PS 读回值 | 一致？ |
|---|---|---|---|---|
| textureBrightness | −27（大怪兽-软铅） | −27 | **−27** | ✅ |
| textureContrast | −17（大怪兽-软铅） | −17 | **−17** | ✅ |
| textureDepth | 4（大怪兽-软铅，最小组） | 41（中间值，用于验证读回） | **41** | ✅ |
| textureScale | 20（大怪兽-软铅/硬铅/万能笔） | 53 | **53** | ✅ |
| 样本上界组合 | b=40、c=6、depth=55、scale=73（大怪兽-碳铅/勾线笔） | 40 / 6 / 55 / 73 | **40 / 6 / 55 / 73** | ✅ |

解析器侧汇总：19 支预设里 **9 支**开启纹理（useTexture=True），全部 textureBlendMode=linearHeight；
取值域 b ∈ [−31, 40]、c ∈ [−50, 6]、depth ∈ [4, 55]、scale ∈ [20, 73]。

**(c) 量程探测（PS 自己接受什么值）**：

| 参数 | 测试值 | PS 行为 | 说明 |
|---|---|---|---|
| textureBrightness | 0 / 100 / 150 / **151** / −150 / **−151** | 全部接受并原样读回 | ActionManager 层**不做** ±150 钳制；UI 滑杆才是 −150..150 |
| textureContrast | 0 / 50 / 100 / **101** / −50 / **−51** | 全部接受并原样读回 | 同上，UI 滑杆 −50..100，接口层不钳制 |
| textureDepth | 0 / 1 / 100 / **101** | 101 → 读回 **100** | 深度上限 100% 生效（钳制） |
| textureScale | 1 / 100 / **1000** | 全部接受 | 缩放无 100 上限（Krita 侧 clamp 0.01..10 是另一回事） |

**(d) 混合模式写入/读回（ABR 里的取值 → PS 读回的成员名）**：

| 实测 charID | PS 读回 | 说明 |
|---|---|---|
| Sbtr | subtract | 对应 ABR Sbtr（减去）✅ |
| Mltp | multiply | 对应 ABR Mul（正片叠底）✅ |
| Hght | height | 对应 ABR Hght（高度）✅ |
| LnHt | height（**未变**） | **PS 2025 的 ActionManager 没有可直接写入 linearHeight 的 charID**（写入被忽略、回读仍是 height） |
| HrdM | height（**未变**） | 同上，Hard Mix 也不能用该 charID 写入 |

**交叉核对结论**：
1. 参数**命名**一致：我们解析的 textureBrightness/textureContrast/textureDepth/textureScale/Txtr.Nm 与 PS 的 currentToolOptions 键名一一对应，写入再读回**逐项相等**。
2. 参数**量程**一致且更宽：我们解析出的 b(−31..40)/c(−50..6) 完全落在 Adobe 文档量程（±150/−50..100）内，PS 接口层甚至不钳制。
3. **一处明确偏差**：ABR 的 linearHeight（9 支笔刷全部用它）**无法用 JSX 的 charID 写入 PS**（LnHt 被静默忽略，回读仍是 height）。
   即：PS 的 JSX 接口暴露的是「height/multiply/subtract...」这组成员名，**不能**用它反查 ABR 里的 linearHeight 语义；
   这条与任务 13 的模式映射（linearHeight→Krita 15）不冲突，但说明「靠 PS 脚本自证 Linear Height 行为」这条路走不通，只能靠真值图/逆向。

## 5. 结论（交给 lead 的一句话）

**未找到可直接采用的 PS→Krita 亮度/对比度映射公式；下一任务指向任务 11（逆向 PS 本体），不是任务 13。**

理由（全部有数字）：
1. B 轴 7 个候选映射（含**现有经验公式基线**）在 148 张真值图上全部不合格：最差 100.00%，平均 77.94%–90.89%；
   现有经验公式平均 80.83%，仅比「恒等不做」的 90.89% 好 10.06 个百分点。
2. C 轴显示跨引擎基线差异本身就有 **22.36%–100.00%**（12 组可核验），绝对 ≤2% 判据不可达。
3. 四条线（开源实现/逆向社区/Adobe 官方/Krita 源码）里**没有任何来源给出 Photoshop 纹理亮度/对比度的计算式**；
   唯一「可执行」的公式都来自 Krita 自己的源码，而它已被证明只在 Krita 侧有效。

**副产品（给任务 11 的输入，不是给任务 13 的公式）**：
- d100 + 位移型模式：PS 亮度 = 精确平移（0.00%，两个独立纹理各复现一次），方向随模式（减去 −B；变暗/正片叠底/线性加深 +B）。
- PS 对比度 = 以 127.5 为中心的分段倍率（0.57%）；pivot 改成 128 立即劣化到 25.89%。
- 深度 <100 与 Height/Linear Height：亮度/对比度**不在最终图上**，只能在纹理层/合成内部解释 → 任务 11 的搜索目标应锁定
  「PS 纹理模式合成链里亮度/对比度插入的位置」，而不是继续找整图 LUT。

**给验收口径的建议（决策项，见 docs/验收报告/10-报告.md 决策记录）**：
≤2% 这个阈值在「PS 图 vs Krita 图」的绝对比对上不可达（基线最小 22.36%）。
若任务 13 要继续用像素判据，应改为**同一引擎内**的口径（Krita 真值 vs Krita 渲染，任务 07 已证明可达 0.00%），
或先在任务 11/13 里解决「PS 与 Krita 基线不一致」这个前置问题。

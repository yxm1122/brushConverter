## 一、结论（先看这一段）

1. **PS 侧角度抖动的单位 = 百分比整数 0..100，既不是「度」也不是「归一化 0..1 值」。**
   三条独立证据（§3.3）：① 读侧把 `jitter` 存成 int32 并 clamp 到 **[0, 上限]**，六个通用动态的上限都由构造函数写成 **100**（`0x141a88cdd / 0x141a88ce8 / 0x141a88cf3` 等，immediate = `0x64`）；
   ② 写侧把该 int 以 **单位 `#Prc`**（`r8d = 0x23507263`）写成 double（`0x141a967e0..0x141a967f2`）；
   ③ 仓库 3 支真实 ABR 的 27 支笔里 `angleDynamics.jitter` 实测 **0..100，单位全为 `#Prc`**（§3.4）。
   → **若单位是「度」，上限应是 360（0x168）；若单位是「归一化值」，上限应是 1。实测都是 100。**

2. **现有 `RotationValue = jitter/100` 映射：量纲成立；Krita 侧「1.0 = 整圈 360°」已由源码定死；只剩 PS 侧「100% = 多少度」待验。**
   `jitter/100` 把「百分比 0..100」变成「0..1 归一化坐标」，与 Krita `RotationValue` 的值坐标 0..1
   （`docs/数据/krita_caps.json:582-594`）**同量纲**。
   Krita 侧本轮把整条链读通了（§3.5.1）：`fuzzy` 传感器是**加法型**、取值 `2r-1 ∈ [-1,1]`；
   `rotationLikeValue` 返回 `wrapValue(…, -1, 1)`；`KisRotationOption::apply` 再算
   `normalizeAngle((1 - value) * M_PI)` → 值域 `[0, 2π]`。
   → **`RotationValue = R` + fuzzy ⇒ 随机旋转跨度 = 360° × R**（R=1.0 就是整圈、R=0.5 是半圈）。
   所以只要 PS 的 jitter 100% 也是「整圈 360°」，`jitter/100` **就是精确映射**；若 PS 100% 只有 180° 跨度才需要 ×2。
   这一步只能靠出图验（§五 第 1 条），**本轮不下结论**。

3. **形状动态的字段来源全部确认成立**（§3.1/§3.2）：`szVr`、`angleDynamics`、`roundnessDynamics`
   三者都是「通用动态子对象」，字段为 `bVTy`(int32, +0x00)、`fStp`(int32, +0x04)、`jitter`(int32 %, +0x08)、
   jitter 上限(int32, +0x0c，仅运行期)、`minimum`(int32 %, +0x10)。`mapping.py` 读的键名/语义/量纲都对得上。

4. **颜色动态：「不可映射」这个旧结论在本轮证据下不成立，应改成「需转换（部分可映射）」。**
   PS 侧抖动发生在 **HSB（HSV）空间**（字段就是 hue / saturation / brightness + purity，§4.3），
   而 Krita 5.3.3 的**像素笔刷引擎本身就有** h / s / v 三条颜色曲线选项 + Mix（前景/背景混合）曲线选项，
   本机 `research/kpp_samples/params_dump.txt` 的 `paintopid="paintbrush"` 预设里 `hValue/sValue/vValue/MixValue` 全在（§4.5）。
   → 结论：**FG/BG 抖动 = 可映射；hue/saturation/brightness 抖动 = 需转换；purity = 不可映射**（§4.6）。
   **注意**：`docs/数据/krita_caps.json` **未覆盖该域**（其 notes 第 644 行明确把颜色动态排除在 `params` 之外），
   按任务书要求这里写「**未覆盖需补查**」，并给出应补条目（§4.5.3）。

5. **顺带发现 2 条映射偏差候选（只登记，不改 `src/`，见 §七）**：
   ① PS 的 `minimumRoundness` **缺省是 25**（不是 0/100），`mapping.py:260-262` 在键缺失时用 `0.0`；
   ② PS 的 `angleDynamics.jitter` 上限 100 而 `scatterDynamics.jitter` 上限 1000（同名字段、不同尺度），
      现有 `÷100` / `÷400` 两套系数不能合并。

6. **未定位（如实）**：**像素消费端**（真正拿这些字段算像素/算旋转的函数）在当前分析状态下**未搜到**
   （§3.7、§4.4）。按团队规则：这是「当前分析状态下未搜到」，**不是「不存在」**。

### 3.3 「PS 侧角度抖动单位是度还是归一化值」——决定性证据

**构造函数 `0x141a88bf0` 给六个通用动态的 jitter 上限统一写了 100（0x64）**：

```text
0x141a88cdd  mov dword ptr [r14 + 0xa4], 0x64   ; szVr.jitter 上限 = 100
0x141a88ce8  mov dword ptr [r14 + 0xb8], 0x64   ; angleDynamics.jitter 上限 = 100
0x141a88cf3  mov qword ptr [r14 + 0xcc], 0x64   ; roundness.jitter 上限 = 100（并顺带把 roundness.minimum 清零）
0x141a88f22  mov dword ptr [r14 + 0x1f4], 0x64  ; prVr（流量）jitter 上限 = 100
0x141a88f46  mov dword ptr [r14 + 0x208], 0x64  ; opVr（不透明度）jitter 上限 = 100
0x141a88f9d  mov dword ptr [r14 + 0x244], 0x64  ; clVr（前景/背景）jitter 上限 = 100
```

（`r14` = 对象基址：`0x141a88c0b mov r14,rcx`；tipDynamics 基址 `0x88` + `angleDynamics` 子对象 `0x24`
→ 上限槽 = `0x88+0x24+0x0c` = `0xb8` ✓ 与解析器读的 `[rbx+0xc]` 对应。）

三条读法互斥检验：

| 假设 | 该假设要求的上限 | 实测 | 结论 |
|---|---|---|---|
| 单位是**度**（0..360） | 0x168 = 360 | `0x64` = 100 | ❌ 否证 |
| 单位是**归一化值**（0..1） | 1 | `0x64` = 100 | ❌ 否证 |
| 单位是**百分比**（0..100） | 0x64 = 100 | `0x64` = 100 | ✅ 成立 |

再看 **写回描述符** 时的单位串（`0x141a96730`，动态子对象 → 描述符）：

```text
0x141a967be  lea rcx,[rsp+0x20]
0x141a967c7  movd xmm3, dword ptr [rbx + 8]     ; jitter（int，百分比）
0x141a967cc  cvtdq2pd xmm3, xmm3
0x141a967d0  movsd xmm6, qword ptr [rip+..]     ; = 100.0 (0x1483d7978)
0x141a967d8  mulsd xmm3, xmm6 ; 0x141a967dc divsd xmm3, xmm6
0x141a967e0  mov r8d, 0x23507263               ; 单位 = "#Prc"（百分比）
0x141a967e6  lea rdx, [rip+..] ; "jitter"
0x141a967f2  call 0x142c5ed90                  ; putDouble(name, unit, value)
0x141a9680e  movd xmm3, dword ptr [rbx + 0x10] ; minimum（百分比）
0x141a9681f  mov r8d, 0x23507263               ; 同样是 "#Prc"
```

**因此：PS 侧的抖动单位 = 百分比（0–100 的整数），不是度、不是归一化值。**
补充对照：**同名字段 `jitter` 在 scatter 里是另一把尺子**（上限 1000）——
`0x141a93120 cmp eax,r14d(0x3e8)` / `0x141a93123 cmovg`（任务 21 §5.1 已记录）。
所以「旋转 ÷100、散布 ÷400」两套系数**不能合并**，这一点本轮得到上限值层面的独立确认。

#### 3.5.1 Krita 侧把「1.0 = 多少度」读通（本轮新增，源码四文件）

| 环节 | 源码事实 | 出处（commit 858d352） |
|---|---|---|
| ① 随机源 | `fuzzy` 传感器 `isAdditive() == true`；`value()` 返回 `2.0*r - 1.0`（r 为归一化随机数）→ **[-1,1]** | `plugins/paintops/libpaintop/sensors/KisDynamicSensorFuzzy.cpp` |
| ② 曲线坐标 → 值 | `rotationLikeValue()` = `KisAlgebra2D::wrapValue(2*offset + constant*(coeff*scaling + additive), -1.0, 1.0)` → **[-1,1]** | `plugins/paintops/libpaintop/KisCurveOption.cpp` |
| ③ 值 → 弧度 | `KisRotationOption::apply`：`value = 1.0 - value`（→ [0,2]）后 `return normalizeAngle(value * M_PI)` → **0..2π** | `plugins/paintops/libpaintop/KisRotationOption.cpp` |
| ④ 比例系数 | `components.constant = m_strengthValue`（即预设里的 `RotationValue`，范围 0..1，见 `krita_caps.json:582-594`）；`scalingPartCoeff = -1.0` | `KisCurveOption.cpp` + `KisRotationOption.cpp` |
| ⑤ 环绕语义 | `wrapValue(value, min, max)` = `wrapValue(value-min, max-min)+min`，而浮点版是 `fmod(x,b)` 后 `if(x<0) x+=b` ⇒ **模 2 环绕到 [-1,1)，不是截断** | `kis_algebra_2d.h`（本地抄录 `research/kis_algebra_2d.h:490-509` 逐行一致） |

→ **结论：Krita 的 `RotationValue = R`（配合 fuzzy 随机）给出的随机旋转跨度 = 360° × R。**
R=1.0 → 整圈（360°），R=0.5 → 180°，R=0.25 → 90°。
所以现有 `RotationValue = jitter/100` 的**物理含义是「PS 的抖动百分比 = 占整圈的比例」**——
只要 PS 侧 100% 也等于整圈，这个换算就是**精确的**（不是「凭手感对上的经验系数」）。

#### 3.5.2 PS 侧「100% = 多少度」的静态取证：阴性结果（如实记录）

为直接定死 PS 侧角度跨度，本轮做了三步扫描，**都没命中消费端**：

| 步骤 | 做法 | 结果 |
|---|---|---|

**给下游的明确结论（不要含糊）**：
- 「PS 抖动单位 = 度」→ **错**；「PS 抖动单位 = 归一化 0..1」→ **错**；**正确：百分比 0..100**。
- `jitter/100` **量纲成立**（百分比 → Krita 0..1 坐标），且 Krita 侧已确定「1.0 = 整圈 360°」（§3.5.1）。
  唯一未定的是「PS 的 100% 是否也是整圈」——若 PS 只有 180° 跨度，则需 ×2。
  **因此本报告不给「已对齐」，只给「量纲与 Krita 侧已对齐，等 PS 侧出图校准」。**
- 顺带一条**正向核对**：`src/brush_converter/kpp/preset_xml.py:458/471` 的
  `RotationValue = max(0, min(100, rotation_jitter)) / 100` 里那个 **clamp 上限 100，与 PS 的运行时上限 100（§3.3）完全一致**——
  这不是抄来的巧合，而是两条独立证据链给出同一个数。

### 3.6 角度坐标系（单独写清，避免 v0.4 手感测试互相矛盾）

### 4.2 ABR 侧结构（交叉验证：clVr 是动态对象，H/Strt/Brgh 是兄弟键）

`tests/海怪笔刷…18支.abr` 的第 17 支「蝴蝶【用数位板】」是全仓库**唯一**带完整颜色动态的样本，实测：

```text
useColorDynamics     = True            (bool)
colorDynamicsPerTip  = True            (bool)
purity               = 0.0             (UntF #Prc)
clVr                 = { bVTy: 0(long), fStp: 1(long), jitter: 0.0(UntF #Prc), Mnm : 0.0(UntF #Prc) }
H                    = 5.0             (UntF #Prc)   ← 色相抖动 5%
Strt                 = 3.0             (UntF #Prc)   ← 饱和度抖动 3%
Brgh                 = 4.0             (UntF #Prc)   ← 亮度抖动 4%
```

读法与 PS 侧结构**完全一致**：`clVr` 是标准动态对象（bVTy/fStp/jitter/Mnm 四件套，对应设置对象 `+0x238..+0x248`），
`H   ` / `Strt` / `Brgh` / `purity` 是**同一描述符里的兄弟键**（对应 `+0x24c/+0x250/+0x254/+0x258`）。
→ 「ABR 的 4CC `H   ` ↔ PS 内部字符串键 `"hue"`」这条对应，由**位置 + 语义 + 单位**三重一致支撑（§七 遗留 2 记一条仍需更多样本的保留）。

### 4.3 「抖动发生在哪个颜色空间」→ **HSB / HSV**（不是 RGB，也不是 HSL）

三条证据：

1. **字段名就是 HSB 三元组**：`hue` / `saturation` / `brightness` + `purity`（§4.1 全表）。
   **没有任何 R/G/B 三元组**；也**没有独立的 lightness 字段**——`"lightness"` 只是 `"brightness"` 的**回退别名**，
   两者写同一个槽 `[rdi+0x1c]`（`0x141a93bc0` 命中就取 brightness，`0x141a93bc9` 否则取 lightness → `0x141a93c04` 单点写入）。
   → 所以**不是 HSL**（HSL 的 L 与 brightness 不是同一概念，若并行存 HSL 会另开槽）。
2. **单位是百分比**：四个键都走 `getDouble` + `#Prc`（读侧 `0x141a93af9` 装载 double 100.0 做恒等换算；ABR 侧 `H/Strt/Brgh/purity` 全 `#Prc`）。
3. **`chroma` 是 `hue` 的回退别名**（同一槽 +0x14），不是独立颜色维度 —— 这条同时排除了「PS 存的是 LCH/色度」这种读法。

> **未判定**：PS 内部到底按 HSB 还是按 **HSV 的 V**（两者在 s=0 时行为不同）做像素运算，本轮没有像素端证据。
> `purity` 的数学定义（把颜色往「纯色」推）也**未判定**。

### 4.4 「抖动顺序」（先色相还是先饱和度）

| 描述符**读取/写回**顺序 | hue → saturation → brightness → purity → perTip | `0x141a93ae1` / `0x141a93b5a` / `0x141a93ba4` / `0x141a93c13` / `0x141a93c51` |
| **像素应用顺序**（先色相还是先饱和度、purity 何时介入） | ⬜ **未判定** | 消费端未定位（§4.5 末尾）。在 brush 窗口按 disp `0x24c/0x250/0x254/0x258` 扫描 **0 命中** |

## 七、遗留与风险（如实，含「本任务未做的事」）

1. **【映射偏差候选 1】`minimumRoundness` 缺省值 25 未映射**：PS 构造函数/解析器缺省 25
   （`0x141a90bbb mov qword[rbx+0x94],0x19`、`0x141a9347d mov eax,0x19`），
   `src/brush_converter/mapping.py:260-262` 在键缺失时用 `0.0` → Krita 允许圆度降到 0，PS 只降到 25%。
   **本任务不改 `src/`**，交 v0.4（见 §九 决策 2）。
2. **【保留】`H/Strt/Brgh` ↔ `hue/saturation/brightness` 的对应仍只有 1 支样本**（§4.2）。语义+位置+单位三重一致，
   但**没有**「同一支笔两侧数值逐一相等」的直接证据 → §五 第 5 条。
3. **`useColorDynamics` 与 clVr 块不同址**（`+0x291` 批量 IO vs `+0x238` 颜色块），且 `0x141a8f9f5` 把 `[rsi+0x292]` 清零，
   这个 `0x292` 的字段名**未定位**（任务 21 把 `wetEdges` 记在 `+0x292`，本处 wetEdges 在 `+0x293`，两者差 1，
   疑为「同一批量 IO 结构在不同装载路径下的基址差」——**未验证**）。
4. **像素消费端未定位**（§3.7/§4.4）：不影响「参数语义/单位/范围」的结论，但**一切「抖动如何变成像素」的因果仍缺**。
   按团队规则记「当前分析状态下未搜到」。
5. **`fStp` 语义未定**：PS 存为 int32（ABR 实测 1..25，不同动态缺省不同：szVr 1、opVr 25），
   本任务只确认它存在、类型与缺省，**没有**确认它是「渐隐步长」还是别的量。现有转换**完全没用它**。
6. **`tiltScale`（+0x04，clamp [0,200]）没有映射**：Krita 的 `tilt` 传感器在
   `docs/parameter-mapping.md:232` 记为 ⛔（`RotationSensor` 只实现 pressure/drawingangle）。
7. **本任务未做**：动态验证（禁止）、Ghidra 反编译（未开 JVM）、间接寻址扫描（方法局限）、
   `docs/数据/krita_caps.json` 补条目（不属本任务写入范围）、`docs/参数矩阵.json` 更新（属 23/29）。

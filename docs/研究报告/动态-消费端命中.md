## 零、结论（四条，全部有原始数据）

1. **硬件断点在 PS 2025 上确实生效，并且有正向证据。** 三重对照：
   - 实验 002 把 DR 断点误下到**栈地址** `0x56558fb808`，44 秒内触发 **200,902 次 `EXCEPTION_SINGLE_STEP(0x80000004)`** —— 这是「断点装上了且在工作」的最强证据（同时也是实验 002 结论不可用的原因）；
   - 实验 003 把 DR 下到**真结构体**后，同一组槽位**既命中写（15 次）又命中读（94 次）**；
   - 命中时被监视地址的取值 `[0, 50, -50, 100, -100]` 与 JSX 依次写入的 brightness/contrast **逐值对应**。
   → 因此本轮所有「未命中」都有对照，不再是上一轮「监控没生效 vs 真没人读」不可区分的情形。
2. **读取者已定位到指令：纹理结构体 `+0x18`/`+0x1c` 的读取全部发生在拷贝层 K60 `0x141ef62b3` 内**
   （`0x141ef62c0 mov eax,[rbx+0x18]` 47 次、`0x141ef62c6 mov eax,[rbx+0x1c]` 47 次，线程 tid=29688）。
   写侧两处：H1 内 `0x141a94a97 mov [rbx+0x18],ebp`（15 次）与描述符内核 `0x1412c4e94b mov [rbx],eax`（31 次）。
   **与静态报告 `静态-纹理.md` §5.2「K60 是拷贝层」的独立判断完全一致。**
3. **绘制期间没有任何线程读这个原结构体**（DR 下发到全部 175–176 个线程，命中只出现在 1 个线程上）。
   但**不能**写成「像素端不消费亮度/对比度」：K60 把值拷到**另一个短命对象**，像素端只可能读那个副本；第二跳（实验 004）只抓到「拷贝对象被 H2 写回侧读回」，**副本之后的去向仍属未判定**。
4. **参数应用通路（本实验触发的那条）是 K91 → {H1, K21, K03, K04, K05, K06, K60}，不是 K01。**
   实验 005 实测：**K01 `0x141a8f520`（9 域装载枢纽）与 K13 `0x141a90410` 在本实验期间 0 次命中**；其余 8 个候选全部命中并达到 15 次上限。
   → 29 号报告把 K01 标为「四域唯一的共同装载入口」在**启动/反序列化**场景成立，但**「改 UI 参数 → 生效」这条通路走的是 K91**，下一轮别再默认 K01 是必经点。

**方法不可行 ①：x64dbg 没有可自动化的驱动入口（如实记录，不是「没试」）。**
- 该安装包里 `x64dbg.exe` 只是 Qt 启动器（字符串表里只有 `GetCommandLineW/CommandLineToArgvW`），调试逻辑在 `x64dbg.dll`；
  `headless.exe` 是**给外部程序通过 X64DBG bridge 通信**的示例客户端，不是「无界面跑脚本」的入口；
  `scriptload/scriptrun` 只能从 GUI 的命令行输入框进 → 要自动化只能写 C++ 插件（本机无 MSVC 工具链验证）或用 UI 自动化敲 GUI。
- 本任务单次实验有 60 分钟上限、PS 会被调试显著拖慢，UI 自动化的失败模式（焦点漂移/弹窗）不可控，故**不采用**。
- **替代方案（本任务实际采用，且与 `ba r4 [reg+0x18]` 逐位等价）**：
  用 Python ctypes 自写调试器（`%TEMP%\bcdyn30\hwdbg.py` + `exp30.py`），走 `DebugActiveProcess` + **CPU 调试寄存器 DR0–DR7**（`GetThreadContext/SetThreadContext` 带 `CONTEXT_DEBUG_REGISTERS`）。
  编码：`Dr0=addr`、`Dr7` 的 `RW=11`（读+写，与 x64dbg `ba r` 同义）、`LEN=11`（4 字节）；命中后用 capstone 5.0.7 反汇编 `Rip` 之前那条指令（x86 数据断点在指令**执行后**报 `#DB`）。
  **注意**：Windows 把数据断点异常报成 `EXCEPTION_SINGLE_STEP(0x80000004)`，与单步同码，靠 `Dr6` 的 `BS(bit14)`（单步）与 `B0–B3`（数据断点）区分。

## 二、方法：这次「未命中」为什么可信

### 2.1 两类断点分工

| 类型 | 做法 | 用途 |
|---|---|---|
| 软件断点 INT3 | 在候选函数入口/快照点写 `0xCC`，命中后**单步重插**（TF+TRAP），每个点最多保留 12–15 次现场 | 取对象地址、统计候选是否被执行 |
| **硬件数据断点 DR0–DR7** | 对**具体字段地址**（`obj+0x18`、`obj+0x1c`）下 4 字节读+写监视，**下发到目标进程全部线程**（175–176 个，`CREATE_THREAD` 里新线程补下发） | 回答「谁读/写了这个字段」 |

纹理结构体地址的取法（**这是本轮最关键的方法细节**）：
- ❌ 在 **H1 真入口 `0x141a937e0`** 取 `rdi` —— 错的：入口处 `rdi=rdx=0x56558fb7f0`、`rsp=0x56558fb708`、`r14=rsp+0x1B0`，**全是调用者的栈地址**；
- ✅ 在 **H1 内部快照点 `0x141a93a79`**（五个字段写完之后，任务 11A 用过同一点）取 `rdi` —— 此时 `[rdi+0x18]`/`[rdi+0x1c]` 就是 contrast/brightness，且必须通过「整数且 ∈[-100,100]」的合理性判据才下发 DR。

### 2.2 正向对照（三重，缺一不可）

| # | 对照 | 原始数据 |
|---|---|---|
| ① 断点触发量 | 实验 002 误下到栈地址 → **200,902 次** `0x80000004`（44 s） | hit-002.json `event_counts["1"]=200902` |
| ② 同地址双语义 | 实验 003 同一组 DR 槽位：**写命中 15 次 + 读命中 94 次** | hit-003.json `aggregate` |
| ③ 取值对应 | `watch_value` 序列 **[0, 50, -50, 100, -100]** = JSX 依次写入的 brightness/contrast | hit-003.json `hw_bp_positive_control.watch_values_seen` + step.log |

### 2.3 踩过的 4 个坑（下一轮直接抄，省 2 小时）

| # | 坑 | 现象（原始） | 修法 |
|---|---|---|---|
| ① | H1 入口 `rdi` 不是结构体 | 实验 002：`rdi=0x56558fb7f0 [+0x18]=-1178081753 [+0x1c]=32759` | 改在 `0x141a93a79` 快照点取 `rdi` + 值域判据 |
| ② | 读上下文不带 `CONTEXT_DEBUG_REGISTERS` | 实验 002 `dr_hit_count=0` 却有 200,902 条 `0x80000004`（命中被当成单步吞掉） | 异常处理统一 `CONTEXT_FULL\|CONTEXT_DEBUG_REGISTERS`，用 `Dr6` 的 BS/B0–B3 区分 |
| ③ | TF 单步重插时 **pending 用全局 set** | 多线程同时命中时 pending 被覆盖 → 某线程 TF 永不清除 → **JSX 线程被单步风暴冻死**（`step.log` 停在 `doc created`，两次复现） | pending 改成 `{tid: {addr}}`，且**任何单步事件都无条件清 TF** |
| ④ | `ContinueDebugEvent` 漏在非异常分支 | 同一症状：`CREATE_PROCESS/CREATE_THREAD/LOAD_DLL` 事件不 continue → **进程附加后直接被挂住**（`step.log` 停在 `doc created`） | 事件循环末尾**统一** `ContinueDebugEvent` |

> ③④ 是两次「PS 看起来卡死」的真因，都不是 PS 的问题，也都不是实验设计的问题；写在这里是因为它们长得和「PS 被调试器搞崩」一模一样。

### 3.1 实验 003：真结构体的读写现场（核心证据）

DR 监视 `0x1de595ed158`(=`obj+0x18`)、`0x1de595ed15c`(=`obj+0x1c`)，下发 176 线程（失败 0）。

| 次数 | 指令（RVA） | 指令文本 | 读/写 | 字段 | 线程 | 调用栈（RVA，前 5 层） |
|---:|---|---|---|---|---|---|
| 47 | `0x1ef62c0` | `mov eax, dword ptr [rbx + 0x18]` | 读 | +0x18 | 29688 | `0xb8843f0 → 0xb8843f0 → 0x1ef1723 → 0xb8843f0 → 0x84bbe8a` |
| 47 | `0x1ef62c6` | `mov eax, dword ptr [rbx + 0x1c]` | 读 | +0x1c | 29688 | 同上 |
| 31 | `0x2c4e94b` | `mov dword ptr [rbx], eax` | 写 | +0x18/+0x1c | 29688 | `0xb8843f0 → 0x1ef2218 → 0xb8843f0 → 0x2c4f344 → 0x2732fb9` |
| 15 | `0x1a94a97` | `mov dword ptr [rbx + 0x18], ebp` | 写 | +0x18 | 29688 | `0x85906d8 → 0x1ef20ae → 0xb8843f0 → 0x2c4f344 → 0x2732fb9` |

**判读**：
- `0x1ef62c0/0x1ef62c6` = K60 `0x141ef62b3 + 0xd/+0x13`，静态报告判它是**拷贝层**（`静态-纹理.md:§5.2` 表里记的就是 `0x141ef62c0 mov eax,[rbx+0x18]`）—— 动态实测**逐指令吻合**。
- `0x1a94a97` 在 H1（`0x141a937e0`）体内 → 参数应用时的**写回**，不是消费。
- `0x2c4e94b` 在描述符内核区（紧邻 K82 `0x142c4e820`），形态 `mov [rbx],eax`（rbx 是调用方传入的字段地址）→ H1 取值路径本身。
- 三个调用者的返回地址都在 `0x1ef20ae/0x1ef2218/0x1ef1723`（= K91 `0x141ef1f90`、K33 附近的参数应用函数）→ **读写全部发生在参数侧，不在绘制侧**。

### 3.2 实验 004：第二跳（K60 拷贝目标）

- 12 次 BP2 命中，`dst=rsi` **每次都不一样**（`0x136b3791f8 / 0x136b37b3d8 / 0x136b378e48 / 0x11d7f693c88 …`）→ 拷贝目标是**短生命期临时对象**。
- 有效命中只有 4 条：`0x1ef62c3 mov [rsi+0x18],eax`、`0x1ef62c9 mov [rsi+0x1c],eax`（K60 自己写副本）、`0x1a96321 mov eax,[rdi+0x1c]`、`0x1a96340 mov eax,[rdi+0x18]`（**H2 `0x141a96230` 写回侧读副本**，与 `静态-纹理.md:§5.3` 记的 `0x141a96320/0x141a9633f` 逐地址对应）。
- 其余 2,996 条命中：2,430 条 Rip 落在 **Photoshop.exe 之外的系统 DLL**、566 条落在描述符内核的堆分配/释放代码上；`watch_value` 有 1,095 条变成非参数垃圾值（典型 `1735289203`=`0x676c6573`）→ **该堆块已释放被复用**，这些命中无意义。
- **结论**：第二跳**只证明了「副本被写、随后被写回侧读」**，没证明「像素端读副本」。→ 见 §五 未判定项。

### 3.4 实验 006：以 K02 为锚点追「纹理参数对象」（方法不可行）

静态报告把 K02 `0x141a8af30` 列为「全库唯一按模式选混合系数」的算术核，形态 `mulss xmm6,[r9+0x18]` / `[r9+0x1c]`（**float**，与描述符侧的 int32 不同）。因此试了「在 K02 入口取 `r9` 当纹理参数对象」。

- 8 次命中里出现**两个不同的 r9**：`0xe04c2fb008` / `0xe04c2fac10`；字段内容 `f32[+0x18]=0`、`f32[+0x1c]=1`、`f32[+0x10]=360`（360 像画布/尺度参数），**且地址全部落在栈区间**。
- DR 下发到这两个栈地址后 800 次命中全是该栈块被反复读写（含系统 DLL 与误码指令，watch_value 退化成 `1.4e-42` 之类 denormal）→ **无判别价值**。
- **但它给了一条有用的线索**：这 8 次命中的返回地址是 `0x1f0177e / 0x1f01a5e / 0x1eff94d / 0x1eff9b7`，再往上是 `0x1f08499 / 0x1f088d5 / 0x2a89e52`，**线程 tid=3300**（与参数应用线程 29688 不同）→ K02 这条链确实在**绘制侧**，30A 若要继续追，应该在这条链上找结构体，而不是用入口 `r9`。

## 五、核心结论与「仍未判定」的边界

1. **谁读 / 谁写（已实测）**
   - 读：K60 `0x141ef62b3` 内 `0x141ef62c0`(+`0x18`)、`0x141ef62c6`(+`0x1c`)；
   - 写：H1 `0x141a937e0` 内 `0x141a94a97`；描述符内核 `0x142c4e94b`。
   - 全部在**单线程 tid=29688**（参数应用线程）上；DR 覆盖全部 175–176 线程。
2. **像素消费端仍属未判定，但范围已被压缩**：
   - 已排除「像素代码直接读这个结构体」——因为若读，DR 必然在绘制线程上命中（机制已自证）；
   - 未排除「像素代码读 K60 造出来的副本 / 读别的派生对象」——副本短命且被堆复用，本轮的监视窗口抓不到；
   - 因此正确表述是：**"纹理结构体 +0x18/+0x1c 的读取点已定位到 K60 拷贝层；像素端消费的是下游副本，链路未打通"**，不能写「与像素无关」。
3. **对 29 号报告的一处口径修正**：K01（9 域装载枢纽）在「改 UI 参数 → 生效」这条通路上 **0 命中**；该通路的真实入口是 K91 `0x141ef1f90`。K01 仍可能是启动/反序列化时的装载入口（那是它的静态证据来源），但**不能默认它是运行期必经点**。

## 六、对任务 30A 的直接建议（改值验证怎么做）

1. **不要**再改 H1 入口的断点（入口 rdi 不是结构体，会重演实验 002）。
2. 30A 的因果验证应当**改 UI 参数 → 看像素**（黑盒差分），而不是继续追结构体指针：
   把 `textureBrightness/textureContrast` 在 JSX 里做 5 档扫描（本任务已验证 8 步 × 3 笔的全流程只需 ~11 s 无调试器 / ~44 s 带调试器），对比导出 PNG 的像素差。
3. 若仍想追副本：在 K60 命中的**同一次事件内**给 dst 下 DR，并**只允许 50 次命中**、命中地址一旦越出 `[base, base+size)` 立即撤断点（本轮就是因为没有这个闸门，3000 次上限被堆噪声打满）。
4. **断点数量要克制**：本任务实测"单个 INT3 + 2 个 DR 槽位"最稳；一次挂 10 个 INT3 会让 PS 的 JSX 时间从 11 s 涨到 25 s 以上。

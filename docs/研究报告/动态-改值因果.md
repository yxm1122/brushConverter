## 零、结论（三条，全部落在数字上）

1. **因果关系成立**：在 K60 拷贝层的**读指令** `0x141ef62c0 mov eax,[rbx+0x18]` 上打断点，命中后把源纹理结构体的两个字段直接改掉，**像素会跟着变**，而且**变得和「在 UI 里改同一个参数」逐字节一样**。
   - multiply：`+0x18` 0→+100 ⇒ 与对照图差 **97.45%**（max_delta **128**）；与「UI contrast=+100」图 **逐字节一致**（diff 0，IDAT 哈希相同）。
   - multiply：`+0x1c` 0→+100 ⇒ 与对照图差 **98.19%**（max_delta **100**）；与「UI brightness=+100」图 **逐字节一致**。
   - linearHeight（depth=10）：`+0x18` 0→+100 ⇒ 差 **67.31%**（max_delta 126），与「UI contrast=+100」**逐字节一致**；`+0x1c` 0→+100 ⇒ 差 **68.05%**（max_delta 100），与「UI brightness=+100」**逐字节一致**。
2. **字段语义被实测钉死**：**`+0x18` = contrast，`+0x1c` = brightness**（int32）。这与 `静态-纹理.md` §5.2 的静态布局判断**独立吻合**，也解释了任务 30 报告里「+0x18/+0x1c」两个偏移谁是谁的问题。
3. **负结果与对照都在**：挂调试器+命中但**不改值**的控制组，与纯黑盒控制图 **diff 0 / max_delta 0 / IDAT 相同** ⇒ 差异只可能来自改值，不是调试器扰动；反向改值（0→−100）同样**逐字节复现**「UI 改到 −100」的图，变化方向正确。

> 一句话：**「读了」升级为「用它算像素」——纹理结构体的 brightness/contrast 在像素通路上是实打实的输入。**

## 一、方法与口径（为什么这样改才算因果）

### 1.1 改值点选在「读指令本身」，不是写在参数应用函数里

| 方案 | 为什么不用 / 用 |
|---|---|
| 在 H1 `0x141a94a97 mov [rbx+0x18],ebp` 改「写进去的值」 | 改了也只是「换个参数值」，和黑盒改 UI 没本质区别，证明不了读侧真的消费 |
| **在 K60 读点 `0x141ef62c0`（本次采用）** | 断点命中时 `rbx` 就是源纹理结构体，**在 `mov eax,[rbx+0x18]` 执行前**改写内存 ⇒ 紧接着的拷贝、以及下游像素都拿到改后的值。这是「改输入 → 看输出」的最短因果链 |
| 在 K60 入口 `0x141ef62b3` | 等价，但取 `rbx` 的时机早一条指令，读数更易受寄存器未就绪影响；读指令处 `rbx` 必然就绪 |

改值实现（单 INT3 + 内存写，不用硬件断点，最省）：

```
INT3 @ module_base + 0x1ef62c0        # 任务30 实测该点每次都读 +0x18（47 次/8 步）
命中 → 取 rbx；读 [rbx+0x18]、[rbx+0x1c]，两个都是 [-100,100] 的 int32 才认（值域判据，防误伤）
     → WriteProcessMemory 改 [rbx+0x18] 或 [rbx+0x1c] 为目标值（本次 ±100）
     → 恢复 0xCC、Rip 回读指令、置 TF、单步后重插
```

单次运行命中 **5 次**（同一次「应用参数」内 K60 被调 5 次），每次都改，全部写成功（`patch_writes=5`）。

### 1.2 三张图构成一组，缺一不可

| 图 | 怎么来 | 作用 |
|---|---|---|
| **控制图** | 同笔、同参（JSX 里 b=0 c=0）、**不挂调试器** | 基线 |
| **改值图** | 同笔、同参（JSX 仍是 b=0 c=0）、挂调试器，在命中点把内存改成 100 | 唯一变量是内存里的那两个 int32 |
| **黑盒同参图** | 同笔、同参，但**在 UI 里**把该参数设成 100，不挂调试器 | 判据：改值图应与它**逐字节一致** |

三张图的 JSX 参数、笔刷（`tests/定量测试专用.abr / 定量测试用`，Dmtr=200 硬笔）、画布（100×100 RGB 透明）、笔迹（路径 (50,50)→(50.4,50.4) 单 dab）、纹理（`research/测试用纹理.png`，invert=true，scale=100）**完全相同**；差别只有「内存值」或「UI 值」。

### 1.3 像素口径

- `tools/imgdiff.py`（任务 03 口径）：只比 Alpha 通道，tol=2/255，分母是全部像素。
- **另加 IDAT 哈希**：文件级 sha256 会被 PNG 的 `iTXt/XMP`（时间戳 + InstanceID GUID）干扰——实测**像素完全一致的两张图，文件 sha256 也不同**（172 个差异字节全在 iTXt 里）。所以本任务额外算 `idat_sha256`（只哈希 IDAT 像素流），`idat_equal=true` 才是「像素逐字节一致」的硬证据。

**改前/改后值的原始证据**（每次命中都记了 `v18_before/v18_after`）：例 `causal-001.json → first_hit`：
```json
{"t_rel": 9.41, "tid": 5884, "rbx": "0x2a6e7797d90",
 "v18_before": 0, "v1c_before": 0, "sane": true,
 "write": [["+0x18", true, 100]], "v18_after": 100, "v1c_after": 0}
```

### 3.1 为什么「逐字节一致」比「差异很大」更有说服力

「改值图和对照图差 97%」只说明「变了」；**改值图与「UI contrast=+100」图 IDAT 哈希完全相同**才说明「变的方式和参数完全一样」。后者排除了「撞大运改坏内存导致画面崩坏」这类假因果：如果只是把内存改花，画面会乱但绝不会**正好等于另一个参数档**。

### 3.2 负对照：`causal-009`（改值效果 = 参数效果，不是「乱改内存」）

linearHeight 在 **depth=100** 这一档，黑盒里把 brightness 从 0 改到 +100 **本来就没有像素效果**（§2.2 最后两行：0.00% / max_delta 0）。在这一档做同样的内存改值（`+0x1c` 0→+100，命中 5 次、写入 5 次），结果是：

- 改值图 vs 对照图：**0 像素差 / 0.00% / max_delta 0**，IDAT 相同；
- 改值图 vs 「UI brightness=+100」图：**0 像素差**，IDAT 相同。

⇒ 改值严格**复制了参数在该档的真实效果**（该档就是没有效果），而不是把内存改坏。这条负对照 + `causal-007/008` 的调试器控制组，一起排除了「差异来自调试器/内存破坏」的解释。

**方向性**（multiply，Alpha 均值）：brightness = **−100 → 194.03，0 → 104.79，+100 → 31.14**；contrast = **−100 → 128.00，0 → 104.79，+100 → 92.03**。单调、符号正确，且每个档位都与对应 UI 档位**逐字节相同**。

## 四、崩溃与稳定性（如实记录）

- **PS 崩溃次数：0**（重试 0/3）。本任务共启动 PS **28 次**：**25 次正常出图**（黑盒 16 次、挂调试器 9 次，全部 `out_exists=true`、`ps_alive_after=true`），另 3 次是调试器缺陷修复前的失败尝试（2 次附加后挂死、1 次 attach-only 诊断，均无出图，已在 §八 记录原因）。
- 调试器观察到的异常：每次挂调试器运行都有一次 `0xe06d7363`（MSVC C++ 异常）**first_chance=1**、地址 `0x7ffc1c8f408a`（系统 DLL 内）——这是 PS 自己 SEH 吃掉的首次异常，**不是崩溃**：其后 JSX 继续跑完并出图（step.log 有 `saved ...`）；记录在每份 causal JSON 的 `crash_event` 字段，未写成「不成立」。
- 调试器本身踩的两个坑（已被修掉，记录以备复核）：① `ContinueDebugEvent` 漏在非异常事件分支 → 附加后 PS 整机挂死（Responding=False）；② 主循环里每轮 `tasklist` 查进程 → 事件排空被拖慢（PS 有 170+ 线程、260+ DLL 事件），JSX 40 s 不动被误判卡死。两处修好后每次运行 ≈12.6 s。

## 五、字段语义：`+0x18` = contrast，`+0x1c` = brightness（实测钉死）

- 静态报告 `静态-纹理.md` §5.2 给的布局是 `+0x18=contrast、+0x1c=brightness`（int32）。
- 本任务实测：**改 `+0x18` 得到的图 == UI 里改 contrast 的图**（multiply dim 97.45%/idat 相同，linearHeight 67.31%/idat 相同）；**改 `+0x1c` 得到的图 == UI 里改 brightness 的图**（98.19% / 68.05%，idat 相同）。两组互换后立即不成立（跨参比对 36%–47%，max_delta 198–226）。
- ⇒ 静态布局判断在**像素层面**得到独立确认。

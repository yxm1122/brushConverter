## 一、任务结论

**任务 20 的结论是「未完成 + 已固化一版可用底座」**，不是「已完成」。

1. **环境已核实并写进报告**：Ghidra 12.2 + Temurin OpenJDK 25.0.5+8；目标 Adobe Photoshop 2025 **26.9.0.15**（`Photoshop.exe`，208,456,176 字节，SHA-256 `05720af2…c953`）。
2. **全量分析未跑完**：累计 5 轮、日志内分析时长 **22,984 秒（约 6.4 小时）**，卡在 **`Constant Propagation`**（从未出现在任何一轮的 analyzer 耗时表里；线程栈证明它一直卡在同一把 `DBHandle` 锁上）。它之后的 `Decompiler Parameter ID` 等**从未开始**（硬证据：`signature_source` 全为 `DEFAULT`）。
3. **已固化的成果**：一轮干净落盘（`C-480`，2026-11-19 23:10:31，日志有 `Analysis timed out at 480 seconds` + `Save succeeded`）包含 **16 个 analyzer 完成**；工程 3,679.8 MB / 10 个文件，**未删除**。
4. **覆盖率三个数字**：总数 **428,344** / 已分析 **424,865** / 未分析 **2**（占非 thunk 的 99.9995%）；更严的口径：代码字节覆盖 **94.05%**，反编译抽样 **200/200 成功、平均 19.5 ms**；与 `.pdata` 独立对照（438,177 条记录、覆盖 `.text` 93.40%）。
5. **对下游最有价值的发现**：**Ghidra 的引用图对键名字符串不可用**（12 个关键地址：capstone 49 条 vs Ghidra 1 条），字符串溯源必须改成「扫描指令操作数」——这直接改变任务 21 的做法。
6. **一句话给使用者**：这次把「反汇编 + 引用 + 跳转表 + 函数发现」这一层做完了（比上一轮多找到 10,276 个函数），但「函数参数恢复」这一层没做；后面做键名/偏移分析够用，但**所有『引用数为 0』的结论都要用第二条独立链复核**。

## 四、还原/复现命令

### 4.1 环境（每个新 shell 都要设）

```bat
set GHIDRA_INSTALL_DIR=<LOCAL_APP_DIR>\ghidra_12.2_PUBLIC
set JAVA_HOME=<LOCAL_APP_DIR>\jdk-25.0.5+8
set GHIDRA_HEADLESS_MAXMEM=13G
set PROJ=%TEMP%\brushconverter-team\ghidra-proj
```

> 注意：本机 `JAVA_HOME` 默认指向 Java 21，而 Ghidra 12.2 要求 Java 25 —— 不覆盖这一条会直接启动失败。

### 4.2 继续跑分析（检查点 7200 s）

```bat
"%GHIDRA_INSTALL_DIR%\support\analyzeHeadless.bat" "%PROJ%" ps_re ^
  -process Photoshop.exe -analysisTimeoutPerFile 7200 -max-cpu 8 ^
  > "%TEMP%\brushconverter-team\logs\20-rerun.log" 2>&1
```

### 4.3 复算覆盖率三个数字（约 1 分钟，不重新分析）

```bat
"%GHIDRA_INSTALL_DIR%\support\analyzeHeadless.bat" "%PROJ%" ps_re ^
  -process Photoshop.exe -noanalysis -max-cpu 2 ^
  -scriptPath %TEMP%\brushconverter-team\task20 -postScript MinimalCoverage.java
```

### 4.4 取完整指标（代码字节覆盖 / xref 规模 / 反编译抽样）

```bat
"%GHIDRA_INSTALL_DIR%\support\analyzeHeadless.bat" "%PROJ%" ps_re ^
```

## 五、遗留与风险

1. **全量分析未完成**：`Constant Propagation` 及其后的 `Decompiler Parameter ID` 等未跑。**所有涉及「函数参数/调用约定」的结论都不可信**；伪代码只能用来看「哪条分支读了哪个字段」，不能用来断定参数。
2. **Ghidra 引用图对 `LEA` 取地址型引用缺失**（实测 49 → 1）：任务 21 及后续凡是要「键名/字符串 → 引用指令」的，必须改用指令操作数扫描或 capstone，不能查 `getReferencesTo`。
3. **函数总数在分析中一路在变**（418,068 → 418,039 → 428,344）：任何引用函数总数的地方必须写明是哪一次测量。
4. **`.text` 还有 5.95%（8,093,052 字节）未定义**：`Function Start Search` 未跑到，这些区间可能有未登记为函数的桩代码（上一轮已见 2 处）。
5. **两轮被 SIGKILL 终止（pass A / pass B / pass L）没有落盘**，那些工作丢失；工程本身未损坏（终止后重新打开正常，日志有 `Save succeeded`）。
6. **工程与日志在仓库外**（`%TEMP%\brushconverter-team\`），不入库：换机器复跑要重新导入（上一轮约 30 分钟），但**不要删本机工程**。
7. **未做的相邻问题**（按铁律 1 只登记）：`CoverageReport2.java` 与 `tools/re_pipeline/GhidraFindCandidates.java` 功能互补但未合并；`tools/re_pipeline/` 是否需要收纳本任务脚本见决策 4。

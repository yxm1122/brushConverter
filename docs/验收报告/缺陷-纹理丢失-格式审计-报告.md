# 缺陷·纹理丢失 — 格式审计 验收报告

- 任务：判断 .kpp 内嵌纹理 resource 写法是否符合 Krita 5.3.3 期望，重点判定 md5 语义与 v1.2.1 引入的「PNG 追加 tEXt」是否反而破坏内嵌纹理加载
- 执行：bugaudit（brushConverter v1.3.0 发布后缺陷排查团队）
- 日期：2026-11-20
- 详细报告：`docs/研究报告/缺陷-纹理丢失-格式审计.md`

## 一、任务结论

**✅ 格式审计有结论：我们的 .kpp 内嵌 patterns resource 与 Krita 5.x 自己的写法同构，md5 计算对象是「内嵌文件字节」而不是像素，
v1.2.1 的 tEXt 属于保护手段、不是破坏；本轮「纹理丢失」在 .kpp 格式层找不到可归因缺陷。**
✅ 自跑的 4 支 GUI A/B 已完成（2026-11-20 11:19–11:21，隔离 profile + 真实 pykrita 插件）：**tEXt 版与无 tEXt 版都让 Alpha 相对无纹理基线大幅变化（28.20% / 37.05% 像素），两种写法下内嵌纹理都被加载并参与渲染**；v1 与 v2 之间 20.90% 的差异来自基线预设自带的随机散布（`ScatterValue=0.3625`），两版内嵌 PNG 解码像素与纹理蒙版完全相同（见 §三-10）。

**审计中另外查实（对根因定位重要）：**用者真实 profile 的当前 DB 里，我们的 bundle **已经注册**（storage id=275、19 预设全 active、md5 19/19 对），
9 个带纹理预设按 Krita 源码语义预测全部可用；但 `memory` storage 里 **没有任何 patterns 行** → 真实 profile 从未真正加载过带内嵌纹理的预设。
因此「纹理丢失/笔刷不可见」更可能是**磁盘 bundle 文件不完整/被删 + 资源缓存 DB 损坏**：bugrepro 已复现 E3（删 bundle → 下次启动静默删除整包 storage+19 预设）与 E5（bundle 截断 → 预设可见可画但内嵌纹理侧载静默失败，Alpha 8844→4672），且该 profile 的 `resourcecache.sqlite` `integrity_check` 实测损坏（`Page 30779 is never used` + 两个资源索引条目数不符）——**不是 .kpp 格式问题**。

## 三、关键数据

### 1. 逐字段 diff（原生 Krita 5.0 样例 vs 我们的 v1.3.0 产物）

| 字段 | 原生 | 我们 | 判定 |
|---|---|---|---|
| `<Preset>` 属性 | paintopid/name/embedded_resources | 同 | ✅ |
| `embedded_resources` | Krita 写资源条数（1 个资源=1） | 固定写 2 | ⚠️ 仅保存侧属性，加载不读（`kis_paintop_preset.cpp:268` 写、`loadFromDevice` 不读） |

| resource `type` | patterns / brushes | 同 | ✅ |
| resource `md5sum` | md5(文件字节) | md5(内嵌字节) | ✅ |
| `Texture/Pattern/Name` / `PatternFileName` | 同 resource name/filename | 同 | ✅ |
| `PatternMD5Sum` | md5(文件字节) | md5(内嵌字节) | ✅ |
| `PatternMD5` | 16 字节二进制（XML 非法字符，Krita 加载时 regex 删除） | 空字符串（Krita 用 MD5Sum 代替） | ✅ 更干净 |
| Texture 参数键集合 | 28 键 | 28 键（diff 为空） | ✅ |

### 2. md5 计算对象（源码 + 实测）

| 层 | 证据 | 结论 |
|---|---|---|
| 算法 | `KoMD5Generator::generateHash(QByteArray)` = `QCryptographicHash::Md5` over bytes（KoMD5Generator.cpp:12-23） | 字节 |
| bundle / folder 资源 | `KisResourceCacheDb::addResources:1238` setMD5Sum(`storage->resourceMd5(url)`)；bundle 版读 zip 成员字节 | 存储的文件字节 |
| 内嵌 / side-loaded 资源 | memory storage 原样存字节（KisMemoryStorage.cpp:203-224）→ resourceMd5（:321-339）= md5(原始字节) | 内嵌原始字节 |
| 实测（原生样例） | brush `9a90b42a…` == md5(PNG) ✅ / != md5(pixels) ❌；pattern `dc4e9099…` 同上 | 排除像素 md5 |
| 实测（我们的产物，v1.3.0 CLI 现场重转） | 22/22 资源 md5sum == md5(base64 解码字节)；9/9 纹理 PatternMD5Sum == 资源 md5sum；9/9 内嵌 PNG 带 tEXt | 自洽 |

### 5. 最小修复方案（格式层：不需要修）

现有写法（content-hash 命名 + tEXt + `PatternMD5Sum`=字节 md5 + `PatternMD5` 留空）在 Krita 5.x 语义下自洽且最优；
**建议不改 src/**。建议只在 `docs/developer-guide.md` 坑清单补两条（文字，非代码）：
1. `PatternMD5` 必须留空；Krita 自己写 16 字节二进制，会在 XML 产生非法字符、加载时被 Krita 自己删除；
2. 「bundle 文件在资源目录 ≠ 已注册」：判断依据是 `resourcecache.sqlite` 的 `storages` 行。

## 五、遗留与风险

1. **GUI A/B 已完成**（方法见 §三-10）；真实 profile 的最终复验属人工步骤（见 §六）。插件必须装真实 `%APPDATA%\krita\pykrita` 且 `--resource-location` 不可用于渲染实验（会静默不加载插件，已由 lead/bugrepro/本审计三方实测）。
7. **使用者侧第一检查项（重要）**：①比对磁盘上的 .bundle 是否为完整文件（大小 29,697,202 B / 22 entries / manifest md5 19/19，`diagnose_profile.py --bundle` 一条命令）；②跑 `PRAGMA integrity_check`；③若 cache 损坏，指导使用者**备份后删除 `resourcecache.sqlite` 让 Krita 重建**（资源文件不动）。不要先怀疑转换格式。
2. **源码版本**：本机 Krita 5.3.3 无公开 tag，引用官方 master commit `6fd9126`；相关加载路径代码 2022 年起稳定（KisEmbeddedTextureData/KisEmbeddedResource 均为 2022 文件），但 5.3.3 私有分支若改动需复核。
3. **用户真实 DB 已被本次（及队友）实验间接影响**：早期一次 `APPDATA` 环境变量重定向对 Krita 无效，那次启动用的是真实 profile，可能触发过一次 Krita 自身的资源库同步（只写 cache DB，未删改资源文件）；之后一律用 `--resource-location` + 副本。副本 DB 已同步出 `海怪…_test.bundle` 的 19 条预设（storage 类型 Bundle），可证明**bundle 能被 Krita 5.3.3 正常注册**。
4. **`converted/*.bundle` 陈旧**（uuid8 命名 + 无 tEXt），不能当发布产物复现缺陷，建议后续清理或加说明（不改 src/，留给 lead）。
5. 本报告不回答「用户真实 profile 里为什么没注册/看不到」的最终根因；那是 bugrepro 的复现任务。本报告只给判据与候选机制（研究报告 §8④）。
6. **真实 profile 的 DB 被本轮排查多次改动**（`memory` storage 时间戳 10:55:01；lead 快照里的 id=271 现已不存在），任何「当前状态」结论都必须配 DB 快照时间；
   团队工具 `krita_render_runner.py` 的 DB 备份/还原会掩盖注册状态，不是「证据」。

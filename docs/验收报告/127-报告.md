## 一、结论：**不可行**

五条判据逐条实测（4 条不成立、1 条仅 4 张部分成立）：

| 判据 | 实测 | 成立？ |
|---|---|---|
| 10/10 张差异比例 0 | **4/10**（并行只产出 4 张；4 张均为 0 差异，其余 6 张无产物） | 否 |
| max_delta 0 | 已出图 4 张 RGB/Alpha **max_delta 均 0** | 仅 4 张 |
| 0 崩溃 | **挂起 1 次**（1 号样本 30.31 s 超时强杀；无异常退出码、无 crash log） | 否 |
| 0 假失败 | **5 次**（另一 worker 的 5 张：进程退出码 0 但无任何产物） | 否 |
| 两个独立 Krita 进程同时渲染 | **不可能**：第二个 Krita 进程 1.70 s 后以退出码 0 转发给已有实例并消失 | 否 |

**根因**：Krita 5.3.3 用 **QtSingleApplication** 做单实例（<LOCAL_APP_DIR> 下 libkritaui.dll 内含该字符串）。同一 Windows 用户会话内只允许 1 个 Krita GUI 实例；第二个进程「转发后退出」，不建窗口、不加载 PyKrita 插件、不落笔。另：本机 **无法为每个进程指定独立 profile**（见 §五），所以任务书要求的「独立临时 profile」也没有可实现路径。

**重要的边界结论（避免误读）**：
- 「并行是否会造成像素差异」**在本机无法被测到**——并行根本得不到两个能渲染的实例；
- 已成功出图的 4 张并行样本与基线 **逐像素完全一致**（RGB/Alpha 差异像素 0、max_delta 0）；串行基线 vs 串行交叉复算 **10/10 完全一致**（两遍复跑指纹也相同）。**失败原因不是像素不一致，而是单实例互斥 + 并发窗口的挂起/假失败。**

**处置**：维持「渲染必须串行」原规则；五条实验按 **128 → 129 → 130 → 131 → 128A** 串行（门未过，不砍机时）。

## 四、串行交叉复算（确定性边界）

串行再渲一遍 10 张，与基线逐张比较：**10/10 全部 IDENTICAL**（RGB 差异像素 0、Alpha 差异像素 0、max_delta 0）；两遍复跑的 kpp/像素/IDAT 指纹也逐张相同。

**结论**：Krita 5.3.3 对这批计算笔刷的**串行渲染是确定性的**；并行门失败与「像素不确定」无关，纯粹是实例互斥/并发干扰。

## 五、根因证据（三条，均可复跑）

1. **单实例机制（决定性）**：
   - 探针：先起 Krita #1，6 s 后起 #2 → #2 **1.70 s 后退出，退出码 0**，#1 仍存活，#2 无窗口、无插件日志；
   - 并发采样：并行尝试期间进程数序列为 [2 × 12 个采样点, 1 × …]，**仅有启动瞬间的重叠**，没有「2 个实例同时渲染」；
   - 证据来源：<LOCAL_APP_DIR> 下 libkritaui.dll 内含字符串 QtSingleApplication；Krita 第二实例走「转发到主实例后退出」的标准行为。
2. **独立 profile 无入口（次要但同样致命）**：
   - CLI --resource-location 能重定向 resources（会新建 resourcecache.sqlite），但实测**导致 PyKrita 插件不加载**：A/B 探针 with_resource_location.plugin_loaded=false / without=true；
   - 子进程环境变量 APPDATA/LOCALAPPDATA 指向临时目录**无效**（Krita 仍读写真实用户 profile；临时目录下无插件日志、渲染超时）；
   - krita.com --help-all 无 config/profile 选项；二进制字符串扫描无配置路径环境变量。→ 任务书硬性要求 3 的「每进程独立临时 profile」在本机无实现路径。
3. **历史记录吻合**：docs/优化提示词/执行进度.md「渲染必须串行」条目（06A 出现幂等用例假失败）；docs/验收报告/33-报告.md §3.3 并发采样 krita 1 个=209 次、0 个=9 次、≥2 个=0 次。本任务把「为什么 ≥2 不可能」钉到了具体机制上。

## 六、对「渲染必须串行」的裁定

**规则维持原文，不改写。** 原规则（执行进度.md 开工前必读第 2 条）：

> 渲染必须串行：同一时刻只允许一个 Krita GUI 渲染会话；与全量 pytest 并发会互相干扰（06A 曾因此出现幂等用例假失败）。跑全量前先确认没有渲染在跑。

**建议在该条后补一句根因（交 lead 回写）**：「根因：Krita 5.3.3 为 QtSingleApplication 单实例，第二进程 1.7 s 转发退出；并行尝试实测 4/10 出图 + 1 挂起 + 5 假失败（任务 127）。」

**若未来 Krita 提供多实例/每进程 profile 能力，重测前置条件（缺一不测）**：
1. 可同时启动两个 GUI 实例的受支持方式；
2. 每实例可指定独立配置目录（kritarc 级，不只是 resources）；
3. PyKrita 插件在独立配置/资源目录下仍能加载；
4. 仍按「10/10 逐像素 0 差异 + 0 崩溃 + 0 假失败」判据。

## 七、决策项（待使用者追认；本轮按推荐项执行）

**D1 并行门结论如何处置？**
1. **接受「不可行」，维持「渲染必须串行」，五实验串行排（推荐）**——利：与判据一致、零返工风险；弊：v0.14 总机时约翻倍。
2. 单独立项「Krita 多实例可行性」改造/换版本后再重测——利：若成功可真正解锁并行；弊：超出本轮范围，且按铁律 12 换 Krita 版本必须重跑全部基准，成本远大于并行省下的机时。
3. 把门判据改为「并行像素等价」另行定义——利：看起来能过；弊：本机无实现路径（两个实例都起不来），等于绕过任务口径，不可取。

**D2 是否把单实例根因写进既有文档？**
1. **写进 Krita 渲染说明「已知限制」+ 执行进度「渲染必须串行」条补根因（推荐，lead 回写）**——利：后人不再误判为「写法问题」重复踩坑；弊：动两处文档，需 lead 统一回写。
2. 只保留在本报告与本地报告——利：零改动；弊：下轮仍可能有人再试一遍并行。

**D3 128 的排期与机时？**
1. **按任务书 1.5–2 小时串行做，之后 129 → 130 → 131 → 128A 依次串行（推荐）**——利：依赖顺序正确（128A 依赖 128 结论）、风险最低；弊：总时长最长。
2. 先做 128A 预烘焙——利：若 128A 能绕开就不必做 128；弊：任务书写明 128A 依赖 128 的结论，顺序倒置会返工。
3. 压缩 128 的样本量/路径数提速——利：省机时；弊：判据从 3×3×2 降档，可能漏掉缩放相位的非线性区，不建议。

**D4 是否接受「并行门在 Krita 升级前不复测」？**
1. **接受，写入已知限制（推荐）**——利：避免每轮重复烧机时；弊：需有人盯 Krita 版本变化。
2. 每轮开工前都重测一次——利：不会漏掉新版本能力；弊：每次约 10 分钟 × 2 遍的无效机时（当前证据已充分）。

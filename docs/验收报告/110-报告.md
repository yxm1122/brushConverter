| # | 文件构成 | PS 结果（原文） | 结论 |

| 4 | 诊断 E：**模板 samp 笔尖、仅换成本生成器的 UUID** | `LOAD_OK` / `SELECT_OK` | UUID 无罪 |
| 5 | 诊断 C：从零 RLE 压缩、无尾块 | 弹窗「不兼容」 | 压缩方式不是原因 |
| 6 | 诊断 F：从零 32×32 原始压缩、无尾块 | 弹窗「不兼容」 | 尺寸不是原因 |
| 7 | 诊断 G：从零 32×32 原始压缩 **+ 8 个 0 尾块** | `LOAD_OK` / `SELECT_OK` | **定位到尾块** |
| 8 | 从零第 2 轮：64×64 + 8 个 0 尾块（最终样本） | `LOAD_OK` / `SELECT_OK` | 成功 |

**根因（有样本证据，不是推断）**：三个样本共 21 个采样笔尖项，像素数据之后**都固定跟 8 个
0 字节**，RLE 与 RAW 一样：

```text
样本逐项统计（测试用.abr 8 项）
item 0  RLE datalen 562  table+rows 554  trailer 8 0000000000000000
item 1  RLE datalen 16618 table+rows 16610 trailer 8 0000000000000000
...
item 6  RAW datalen 350  pixels 342     extra 8    0000000000000000
```

漏掉这 8 字节时，本项目自己的解析器照样能读（`_decode_pixels` 只取前 `width*height`
字节），但 PS 直接判整份文件不兼容——这是本任务最关键的写入侧坑，已写进生成器注释。

## 五、8BIM 对齐与 enum 顺序的实现证据

### 5.1 8BIM 对齐必须是 `(-length) % 4`

代码（`tools/make_test_abr.py:253`）：

```python
pad = (-len(data)) % 4
return b"8BIM" + key.encode("latin1") + struct.pack(">I", len(data)) + data + b"\x00" * pad
```

最终文件的区段实测（`one-test.abr`）：

| 区段 | 数据长度 | `length % 4` | 实际补足（`(-length)%4`） |
|---|---|---|---|
| samp | 4428 | 0 | 0 |
| desc | 758 | 2 | 2 |
| phry | 233 | **1** | **3** |

phry 区长度 233：按 `length % 4` 会补 1 字节，下一段起点会偏 2 字节；本次按 `(-233)%4 = 3`
补足，扫完正好停在文件末尾 5464（见上表「下一段」累加）。这就是铁律里那个历史坑。

### 5.2 descriptor enum 顺序：先 typeID、后 value

代码（`tools/make_test_abr.py:191`）：

```python
# 规范顺序：typeID 在前，enum 值在后（descriptors.py:160）
return b"enum" + _id_bytes(str(v.type_id)) + _id_bytes(str(v.value))
```

与解析器 `src/brush_converter/abr/descriptors.py:160-164` 的顺序一致；从零预设在
`toolOptions` 之外没有用到 enum，但模板路线改写 `textureBlendMode` 等键时走同一分支，
PS 打开模板文件成功（`LOAD_OK`）说明这个顺序在 PS 侧也成立。

### 5.3 其他由样本实测确定的写入约定

- 文件头 `>HH` = 6.2；区段顺序 `samp → desc → phry`（无 `patt` 也能打开，模板路线已实证）。
- 采样笔尖头 301 字节：`[37]=0x00010000`、`[41]=3`、`[65]=56`、`[289]=1`、`[297]=8`
  照抄样本常量；`[45]=项长-49`、`[293]=像素数据长+15`（21 个样本项逐项核对）。
- 像素后固定 8 个 0 字节（本任务实测的必需项，见第三节）。
- desc 的预设键集取「海怪样本第 1 个预设」的最小 14 键结构 + `Brsh.Hrdn`；PS 能打开，
  说明缺省键有默认值，不需要把 40 多个键全写出来。

# 排错手册：按你看到的现象查

Troubleshooting for the published v1.6.1 Windows workflow, with older-version risks and remaining untested behavior clearly separated. It covers safe cancellation, configuration errors, bundle tag scope and the known CLI-redirection and same-name import issues; cache rebuilding is optional and may lose custom tags or groups.

[返回首页](<../README.md>) · [用户指南](<user-guide.md>) · [正确导入方式](<user-guide.md#import-krita>)

**先保留原始信息，再处理**：完整错误文字/日志、所用版本与获取渠道、ABR 文件名、输入/输出路径（对外分享时脱敏）、选的输出格式、预设数/真实纹理数、资源包名和退出码。GUI 报错请原样记录，不只说“不能用”。不要删除原素材、批量清空资源库或在原目录反复重转覆盖现场。

<a id="invisible-texture"></a>
## 一、笔刷不可见 / 纹理像丢了

**第一检查项：别把原始 `.abr` 直接导入 Krita。** Krita 的 Adobe Brush Library 直读得到的是另一套笔刷，没有经过本工具的纹理转换；它与转换产物同名时会混淆判断。这是[既有缺陷复盘](<../releases/RELEASE_NOTES.md>) v1.3.1“根因说明”中的实测原因，不能据此断言每次不可见都由它造成。

按代价从小到大排查，任一步解决就停，不要求全部执行：

1. **核对来源**：在资源管理中确认实际选用的是本次生成的资源包/预设，而非同名 ABR 直读库。若已误导入，在备份后只停用/移除已确认的 ABR 库；也可正常退出 Krita 后，把资源目录中该 ABR 的已导入副本移走备份，再启动。**后果**：该直读库的预设会离开当前列表；不要删除本工具使用的原始 ABR，不动其他资源。
2. **核对转换摘要**：资源包应无回读失败；预设数应大于 0，真实纹理数按本次输入而变。源笔刷纹理关闭、图案缺失或只有 1×1 占位纹理时，不该期待可见纹理；“真实纹理 0”不能单独判定缺陷。必要时使用[只读诊断](<#readonly-diagnosis>)，不硬套某个旧样本的条目数。
3. **核对资源形态（D-6）**：不要同时导入同一批的 bundle 与散装 KPP。两者预设文件名相同，Krita 按文件名跨来源去重，后一来源可能被静默忽略；移除生效那份并重启后，预设可能消失而标签残留（2026-11-27 实测）。要单独用散装 KPP，先备份并移除同批 bundle，只核对一种形态。
4. **核对已加载版本**：更新资源前先正常退出 Krita，备份旧文件后再替换、启动；不要在程序运行时覆盖已加载的包。见[正确导入/更新](<user-guide.md#import-krita>)。
5. 仍无法解释时，保留诊断原文与实际现象，标**待验证假设/待回填**，不要直接定成“纹理格式坏了”。[缓存重建](<#cache-rebuild>)仅是自愿的最后兜底，不是前置条件。

<a id="conversion-error"></a>
## 二、转换报错 / 输出校验失败 / 预设数为 0

先保存报错全文、完成摘要与退出码。CLI 的 `convert` 与诊断工具的退出码**不是同一套含义**。

| 看到什么 | 当前含义 | 接下来做什么 |
|---|---|---|
| `convert` 退出码 0 | 命令正常结束 | 仍需有非零预设输出、核对“跳过”与回读摘要；不代表导入或外观通过 |
| `convert` 退出码 1 | 输入、读写或内部错误 | 原样保存原因，核对输入与目录；v1.6.0 隐藏原名/路径，不因此当作没有错误 |
| v1.6.0 的 `convert` 退出码 2 | 配置/选择错误、零源或全部跳过，也包括 argparse 错误 | 查 `--help` 与错误码，核对两类 JSON、源摘要和稳定 ID；不回退默认掩盖坏输入 |
| `convert` 退出码 3 / “输出校验：失败” | v1.6.0 的安全写出/回滚/校验失败；v1.5.0 及更早版本主要是包回读失败 | **不要导入未确认交付的文件**；保存 blocked/rolled_back/retained 明细，不能把部分受阻当完整回滚 |
| v1.6.0 的 `convert` 退出码 130 | 协作取消完成或取消异常出口，不是成功 | 核对交付与清理/保留清单，等停止后按[取消恢复](<#cancel-recover>)处理 |
| GUI 报失败/部分受阻，或旧版“完成”内附回读失败 | 不是合格整批交付 | 不以标题、满进度条或“已处理”计数当成功，保存完整原始详情 |
| 0 个预设 / “无笔尖位图”被跳过 | 没得到完整可用的输出，或部分预设不可转 | 核对原始 ABR 与解析警告；不要将部分文件当整批成功 |
| 提示两个输出都关闭 | 同时用了 `--no-bundle` 和 `--no-standalone` | 至少保留一种输出；这不是无写入预演参数 |
| 已交付且回读 OK，但重定向或管道后退出 1，报 U+2212 编码错误 | 已知 D-2：系统代码页为 936 时，打印替代理由可能失败；不等于产物校验失败 | 保存报错和原目录，先核对实际产物；需要重跑时用新的输出目录和真实控制台直连（已验正常），不要因退出 1 盲目覆盖或判成未写出 |

可选的 `info` 子命令按是否存在采样笔尖决定退出码：退出码 2 不等于计算笔刷一定无法转换；别把它当所有 ABR 的“允许转换门”。
缺依赖或源码启动失败时，先核验 Python ≥3.12 与实际解释器，见[源码运行](<user-guide.md#source-run>)；exe 用户不必为此安装开发环境。

<a id="output-location"></a>
## 三、有文件却找不到，或只有一种格式

- 看**本次完成摘要**指向的输出目录，不凭上一次目录或文件时间猜。默认目录与工作目录有关；使用显式 `-o` 或 GUI 选择的新目录最清楚。
- GUI 一次二选一；CLI 默认两种都有，`--no-bundle`/`--no-standalone` 会分别取消一种。资源包在输出根目录，独立 KPP 在 `kpp/`，详见[输出位置](<user-guide.md#outputs>)。
- “已存在同内容产物，未重复写入”是复用提示，不是失败；v1.6.0 的独立 KPP 也有复用/冲突顺延保护。当前 CLI 隐藏文件名/绝对路径，按自己给的目录、产物编号和摘要核对，不沿用上次包名。
- **v1.5.0 及更早版本的独立 KPP** 仍可能覆盖；v1.6.0 虽增加整批保护，也不能承诺强杀、磁盘/清理故障下全有或全无。不要在旧目录反复试验或自动清理现场。
- 提取（`extract`）输出的 PNG 和 JSON 只是采样笔尖与信息，不是可直接替代 KPP 的预设。

<a id="old-preset"></a>
## 四、更新后仍像旧版 / 曲线与传感器异常

1. 核对正式下载渠道、发布提交与实际导入文件，不只看名字；v1.6.0 已发布，但正式包仍保留追溯构建状态字面值 `unreleased`（未重打包），旧实验可能仍带 1.5.0。见[版本区分](<user-guide.md#candidate-status>)，不要改写旧样本伪造新版证据。
2. 若是旧版产物，先读[版本说明](<../releases/RELEASE_NOTES.md>)对应升级注意，用所选版本重新转换到新目录。新程序不会自动改写已经生成的旧 KPP/bundle。
3. 正常退出 Krita，备份旧测试资源，只替换已确认的旧产物后重新启动，避免新旧同名资源混用；不要直接清空整个库。
4. 早期空传感器 XML 已在已发布版修复，不能把旧产物的曲线异常一概归为 Krita UI 缺陷；仍有异常就附原始日志与来源；发布验收的 30 项通过不代表任意笔刷或组合都已验证。

v1.5.0 的历史升级与当前 v1.6.0 升级不是同一件事：v1.6.0 另有亮度越界区预烘焙、旋转抖动修正，相关旧产物须按当前版本说明从原 ABR 重转。不要把 v1.6.0 的新增能力套到 v1.5.0 及更早版本。

<a id="appearance"></a>
## 五、外观有差异 / 某些设置不能再调

- 先确定源笔刷是否真的启用了纹理，以及是否选中了转换产物；不是每支笔刷都应该画出纹理。
- **硬度、纹理缩放等的编辑代价**不等于文件损坏。v1.6.0 可在“逐支处理与编辑能力”关闭对应适用项后从 ABR 重转，保留受限原生字段，并承担外观/范围代价；不是在 Krita 里取消已烘焙像素。见[取舍表](<user-guide.md#tradeoffs>)，legacy 公式环境变量仍已删除。
- 纹理模式不是全部精确等价：如 hardMix 有条件残差，Drkn 没有等价承载；详细条件只查[映射参考](<parameter-mapping.md>) §7.2、§10，不复制或另造结论表。
- 已证实的残差、已知缺失、**待验证假设**分开说。单凭截图、控制值看起来不同或机器校验成功，都不能裁决实际笔触一致；记录输入条件并等待有证据的判断，不擅改公式或旧基准。

<a id="planned-features"></a>
## 六、找不到开关、标签或元信息表单

先核版本：这些控件已包含在 v1.6.0 正式包中，位置见[GUI 步骤](<user-guide.md#gui-convert>)；v1.5.0 及更早下载包没有这些新增控件。请从[正式发布页](https://github.com/yxm1122/brushConverter/releases/tag/v1.6.1)获取正确版本，不能仅凭 exe 文件名判断来源。

- 列表只有一部分时看“隐藏已选”；全选/取消仅作用可见行，清搜索并恢复“全部笔刷”后再核总数。切语言不丢设置，换源/重载会恢复条件默认与本批元信息/标签。
- 元信息表停用先看格式：独立 KPP 不承载包信息、原生标签与追溯。v1.6.0 的 CLI 要显式加 --metadata-file 才启用新链，GUI 空表单与无配置 CLI 不等价；--no-bundle 与该配置冲突会退出 2。
- 标签异常先看“最终标签及来源关系”和回读摘要：来源可改删、单支移除优先。未知/未选中 ID 要修配置，不会静默丢字段。只改说明/标签也产生新身份，旧包不会自动更新；保留两版，不混装来源。
- 文件回读只是机器证据。使用者集中验收已记录已验项目，但 E4/E6/F1/F3/F4/G3 六项仍未验、条件放行；具体边界见[正式版与验收说明](<user-guide.md#candidate-status>)。不能据此推广到所有逐笔筛选、同名关联与重启组合，也不能只因 XML 有字段就关闭问题。包内标题、包版本/来源/追溯的显示限制见[包信息说明](<user-guide.md#metadata-tags>)；重存可能丢自定义字段，保留原导出包。

<a id="cancel-recover"></a>
### v1.6.0 取消、部分受阻后如何恢复

1. 保存原始提示、阶段、交付状态与 new/reused/renamed/blocked/rolled_back/retained 计数；GUI 清单原样留存，CLI 按指定目录和产物摘要核对，不删除旧文件。
2. “请求已接收”不是已取消；等线程安全结束。最终交付期不可取消，迟到请求以实际完整交付/失败清单为准，不强杀应用。
3. 仅在确认取消且清理完成后，核对选择/开关/标签，换新目录重新开始；没有断点续转。解析取消或源字节改变需重新载入，随后手动设置已重置。
4. 部分受阻、回滚或清理失败时保留暂存目录与事务清单，停止自动重试/删除，交原始证据确认能处理的本批文件。关窗“取消关闭”也不会撤回已发停止请求。

<a id="readonly-diagnosis"></a>
## 七、需要更多证据：可选只读诊断（源码用户）

**不是必做步骤，exe 包用户可先提供现有报错。** [只读诊断脚本](<../tools/diagnose_profile.py>)需要完整源码和已配置依赖的 Python；没有现成环境时不要为排错盲目安装。
它不启动 Krita、不写用户资源库，但会复制缓存数据库到临时目录并写日志；`--predict` 会额外解码图案、较慢，**预测不等于实机落笔或导入成功**。

在项目根目录**另开一个 PowerShell 窗口**，先按[源码运行](<user-guide.md#source-run>)设置并核验 `$PY`；核验失败就停止。把包路径改成本次实际文件名，并先确认 Krita 的实际资源目录。以下只改当前进程的临时环境，结束关闭这个窗口即可，不修改系统配置：

```powershell
$Work = Join-Path (Get-Location) '.tmp/user-diagnose'
$Temp = Join-Path $Work 'temp'
New-Item -ItemType Directory -Force -Path $Temp | Out-Null
$env:TEMP = $Temp
$env:TMP = $Temp
$env:TMPDIR = $Temp
& $PY -B -c "import os,tempfile; assert os.path.realpath(tempfile.gettempdir()) == os.path.realpath(os.environ['TEMP']); print('临时目录核验完成')"
if ($LASTEXITCODE -ne 0) { throw '临时目录隔离失败，停止。' }
# 默认位置仅作示例；自定义资源目录必须按实际路径修改。
& $PY -B tools/diagnose_profile.py --krita-dir "$env:APPDATA/krita" --bundle ".\output\run-01\实际文件名.bundle" --predict 2>&1 | Tee-Object -FilePath (Join-Path $Work 'diagnose.log')
$LASTEXITCODE
```

看每节原文，不套固定条目数：是否有 ABR 直读库、同名来源、包条目/manifest 校验失败、数据库是否注册。诊断退出码 **0=未发现问题、1=发现问题、2=参数或读取错误**；跳过的节不算通过。该工具显示的“建议删除缓存”也不构成自动授权，仍须读下一节的备份与损失说明。

**后果与隐私**：诊断不删除配置，但本地临时副本/日志可能含资源名和本机路径；对外提供前脱敏，不上传无权公开的原始 ABR、商用素材或整份个人资源库。个案诊断以你本次输出为准；本文示例不表示你的用户库已检查通过。

<a id="cache-rebuild"></a>
## 八、资源仍异常：重建缓存（可选，最后兜底）

**不是修复 ABR 直读冲突的必要步骤，也不是导入前的准备动作。** 仅在来源、产物与加载版本检查无效，且你接受以下损失时考虑：

1. 正常退出 Krita，确认应用已完全结束；不要强杀线程或直接在运行中动数据库。
2. **整份备份实际 Krita 资源目录**（常见默认位置为 `%APPDATA%\krita`，以实际配置为准），保留可恢复的原件；备份没确认就停止。
3. 只把该目录中的 `resourcecache.sqlite` 改名留备份，再启动 Krita 等待重新建立缓存。不要删资源目录，也不要同时清理其他文件。
4. 核对资源与原有分类；发生意外先保留新旧现场，正常退出后再求助，不保证简单改回单个数据库就能恢复所有状态。

**明确代价**：自定义预设标签/分组会丢失，需要重新整理；笔刷/图案等资源文件本身不会因缓存重建而被删除，但这不是“无需备份”的保证。重建耗时取决于资源库大小，不承诺固定几分钟。历史依据见[版本说明](<../releases/RELEASE_NOTES.md>) v1.3.1“根因说明”；是否需要、是否有效取决于你的实际问题，不因版本已发布就保证缓存重建有效。

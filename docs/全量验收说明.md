# 全量验收说明（任务 15 · verify_all）

> 说明：本文档里的本机实测路径已占位化（`<LOCAL_APP_DIR>` = 本机软件安装目录，`<REPO>` = 仓库根），复现时请改成你自己的安装路径与仓库路径。

> 工具：`tools/verify_all.py`。一条命令依次跑「参数层 → 像素层 → 手感层」（**严格串行**），
> 打印「层 / 通过 / 失败 / 跳过 / 关键指标」总表 + **与任务 01 一字不差**的摘要行，并支持归档与清单合并。

## 1. 怎么跑

```bash
cd <REPO>
# 只跑并打印（退出码：0=全通过；1=有失败/异常；2=一条用例都没收集到）
python tools/verify_all.py

# 跑完写归档：docs/验收报告/归档/verify-<YYYYMMDD-HHMMSS>.md（同名自动加 -2、-3，不覆盖）
python tools/verify_all.py --archive

# 把 tests/baselines/feel/manifest.json 合并进顶层 tests/baselines/manifest.json（幂等）
python tools/verify_all.py --merge-manifest

# 自检：追加一个临时失败用例（建在系统临时目录，跑完即删），验证失败明细与退出码
python tools/verify_all.py --selftest-failure

# 可选：把结构化结果另存 JSON；调整单层超时（默认 900 秒）
python tools/verify_all.py --json /tmp/verify.json --timeout 600
```

**发版前必跑**：`python tools/verify_all.py --archive`，只有「失败 0」才继续。

## 2. 三层分别跑什么

| 层 | 实际命令 | 当前用例数 | 关键指标列 |
|---|---|---|---|
| 参数层 | `pytest -m verify_params` | 3 | 用例数与通过数 |
| 像素层 | `pytest -m verify_pixels` | 34 | 用例数与通过数 |
| 手感层 | `pytest tests/test_feel_curve.py` | 9 | feel 基线条数、自比 max dev、压感是否真实注入 |

手感层的「关键指标」直接读 `tests/baselines/feel/manifest.json` 逐条做自比（应恒为 0），
基线缺失时该层如实 skip，不允许算成通过。

## 3. 输出格式（脚本可解析）

顺序固定：表格 → 失败明细 → 跳过明细 → 分隔线 → **摘要行（最后一行）**。

摘要行复用任务 01 的契约（`tools/verify_entry.py` 的 `build_summary`）：

```text
通过 N 项 ｜ 失败 M 项 ｜ 跳过 K 项
```

注意「｜」是 U+FF5C 全角竖线；有跳过时末尾追加「（含跳过，未全验）」，且**跳过不计入通过**。

退出码与任务 01 一致：

| 退出码 | 含义 |
|---|---|
| 0 | 全通过（含跳过：摘要带提示，仍为 0） |
| 1 | 任一层有用例失败，或 pytest 异常/超时 |
| 2 | 三层一条用例都没收集到（标记/路径配置坏了） |

## 4. 归档文件

- 路径：`docs/验收报告/归档/verify-<YYYYMMDD-HHMMSS>.md`；同一秒重复运行自动加 `-2`、`-3`，**不覆盖历史**。
- 内容四节：
  1. 归档时间 / 命令 / 退出码 / 摘要行；
  2. 总览表（层/通过/失败/跳过/关键指标 + 合计）；
  3. 失败明细（`[层] 文件::用例`）；
  4. 跳过原因（`[层] 文件::用例 — 原因原文`）；
  5. 运行环境**自动采集**三行：Python（platform）、Krita（`krita.com -v`）、Photoshop（PowerShell 读 exe FileVersion）；采集不到写「未检测到」。

## 5. 清单合并（feel → 顶层 manifest）

`--merge-manifest` 的规则（沿用任务 09 的合并口径）：

- 合并键：顶层 `file` 相对路径（`feel/<原文件名>`），已存在则跳过 → **幂等**；
- 每条固定 11 字段（file/source/size/pressure/mode/depth/brightness/contrast/status/alpha_nonzero/note），缺的写 null；
- `alpha_nonzero` **当场读 PNG 实测**，不抄子清单；
- 来源记为 `krita`（手感图确实是 Krita 渲染），`sources.feel` 保留子清单出处；
- 条数对账写进 `counts`（ps/krita/handmade + reconciliation）与 `merge_history`（时刻/新增/重复跳过/合并前后条数），顶层 `merged_at` 记录合并时刻。

本次对账：**341 = 329（合并前）+ 12（feel 新增）**；`counts = 341 = 298(ps) + 41(krita) + 2(handmade)`；
第二次重跑 `added=0, duplicates_skipped=12`。

## 6. 已知冲突（发版前必须处理）

`tests/test_assembly.py`（任务 09 的组装验收）有两条断言按「三源口径」写死：

1. `test_top_manifest_reconciles_at_merge_time`：要求 `item.file` 的路径前缀 == `item.source`；
2. `test_naming_compliance_registered_only`：结构性命名检查同样要求第 1 段 == source。

任务 15 按任务书把 feel 基线条目并入顶层清单后，这些条目的 `file` 是 `feel/feel__...png`、`source` 是 `krita`，
于是这两条用例失败（1 条 `test_sources_have_not_drifted_since_merge` 因计数漂移如实 skip）。
这是**任务书要求与 09 旧断言的结构性冲突**，不是并行代理的临时状态；本任务写入范围不含 `tests/test_assembly.py`，
所以只能如实报告，不改别人的文件。建议 lead 二选一：

- **A（推荐）**：由任务 16/09 把「三源」扩为四源（`feel` 成为正式 source，`file` 前缀 `feel/`），改 2 处断言；
- **B**：保持三源，把 feel 的 12 张图复制进 `tests/baselines/krita/` 并改名为 `krita/feel__...`，顶层登记随之调整（会与任务 14 的 feel 子清单重复一份图）。

在冲突解决前，全量结果会显示「失败 2 项 ｜ 跳过 1 项」，**不代表参数/像素/手感三层本身有问题**；
合并前那次归档（`verify-20261118-232059.md`）是 46/0/0 全绿证据。

## 7. 失败时先看哪一层

1. 先看摘要行失败数；2. 看「失败明细」定位到用例；3. 单独复跑该层：

```bash
python -m pytest -m verify_params -v
python -m pytest -m verify_pixels -v
python -m pytest tests/test_feel_curve.py -v
```

## 8. 并发约束（重要）

- `verify_all.py` 三层是**串行**的：同一时刻只启动一个 pytest 进程；
- 会启动 Krita GUI 的用例（`tests/test_krita_render.py`，任务 06）**不在三层内**：Krita GUI 渲染同一时刻只能一个会话，
  与批量渲染/其他 pytest 并发会互相干扰（任务 06 已实测踩坑）。要跑它们请单独、串行执行；
- 手感层只读基线图与曲线 JSON，不启动 Krita。

```bash

# 4) 清单合并幂等（第二次应显示 新增 0）
```
